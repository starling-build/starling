Starling Desktop · Performance Report

Starling’s terminal against Ghostty

Ten throughput workloads, three runs each, at an identical 47×201 grid. Against the Ghostty in Ubuntu’s archive, TerminalApp wins the suite. Against Ghostty’s nightly, built from today’s source, it does not: the nightly is 1.43× faster than the shipped build, and against the Swift TerminalApp it won the suite 3.998 s to 4.535 s. Moving our emulator core from Swift to C reversed that: 2.618 s against 3.998 s, on half the CPU. Ghostty’s own three published tests are reproduced here across five terminals, where the headline holds and TerminalApp comes second on ASCII, third on DOOM-Fire and last on Unicode. Memory remains our clear loss, and it does not stop climbing.

1 · The measurement

The harness is the one already in the tree at test/bench/. Each workload is a pre-generated file (419 MB of corpus in total) that the runner cats into the terminal it is running inside; the page cache is warmed first, so no test pays for disk and the producer costs the same on both sides. The runner reads the terminal’s own utime+stime out of /proc around each cat, which is why CPU can be attributed to the terminal rather than guessed at.

Three consecutive suites per terminal per desktop, every run in the table in §7. The spread is small enough that the ranking never depends on which run you pick: the widest run-to-run spread on any single workload is 7.8%, and most are under 3%.

It was measured twice, because the first round had a flaw. Round 1 ran both terminals in a Starling session as the unprivileged session user (uid 1001) through a real GDM login — but the two windows did not get the same grid, which taxes the cell-bound workloads unequally. Round 2 removed that: TerminalApp was built against the engine’s GTK embedder (libflutter_linux_gtk, FlView in a GtkWindow) so it runs as an ordinary Wayland client, and both terminals were then run in a GNOME session pinned to an identical 47×201 grid. Round 2 is the headline number; Round 1 is kept because it is what motivated Round 2.

The grid is the thing to control for. In Round 1 Ghostty’s window came to 45×201 (9,045 cells) and TerminalApp’s to 52×241 (12,532) — 39% more cells, because its bundled RobotoMono sets a smaller cell than Ghostty’s default face at the same window size. Every row-sized and frame-sized cost (scroll fills, blank-row memmoves, rows repainted per frame) scales with that, while parse-bound cost does not, so no single correction factor fixes it. In Round 2 both were pinned to 47×201 — Ghostty maximised, TerminalApp given a window sized to land on the same grid — and every grid read with stty size from inside the terminal itself. Nothing below needs adjusting.

2 · Round 1 — where the margins come from

The suite splits cleanly into two regimes. On bulk text — dense rows, autowrapped long lines, alt-screen repaints, region scrolling, random bytes — TerminalApp is between 1.6× and 3.0× faster and uses a quarter to a half the CPU. This is the run-based write path: scan forward for a span of plain printable ASCII and fill it through one withUnsafeMutableBufferPointer, instead of paying Swift’s exclusivity and copy-on-write checks per character.

On escape-heavy input the two converge. sgr_fg and sgr_truecolor put an SGR sequence in front of every single cell, which defeats the run scanner by construction — there is never a run longer than one character. What is left is the CSI parser and the per-cell style resolution, and there Ghostty’s costs less CPU than ours. We still finish those two workloads slightly sooner in wall-clock (1.11 s vs 1.19 s; 1.14 s vs 1.25 s), because the repaint cap keeps the render thread from serialising behind the parser, but we spend ~38% more CPU to do it.

cursor_motion is the only wall-time loss and it is not worth chasing: 400,000 cursor addressings land in 49 ms for us and 46 ms for Ghostty, and our cost per addressing is below the timer resolution the harness can honestly report.

3 · Round 2 — GNOME, at an identical grid

TerminalApp’s widget tree is host-neutral: runStarlingApp composites as a DMA-BUF child when the shell’s socket is in the environment, and otherwise hands off to a windowed host. Linking the SDK’s FlutterGTK and calling GTKWindowedHost.install() gives it the engine’s GTK embedder, so the same terminal sources run as an ordinary GTK3 Wayland client. That build is opt-in (STARLING_APP_GTK=1) and the shipped binary’s link set is unchanged — GTK appears in one and not the other.

With both terminals on GNOME Shell 50.1 (Wayland) at 47×201, TerminalApp takes 4.54 s / 7.39 CPU-s against Ghostty’s 5.71 s / 9.96 — 0.79× the wall time and 0.74× the CPU, ahead on 7 of 10 workloads and cheaper on 8.

4 · What the compositor costs — the same binary on both desktops

Ghostty is one unmodified binary, so running it on both desktops isolates the compositor cleanly in a way TerminalApp cannot (its two builds use different embedders). Across the suite Ghostty is 1.11× slower in wall time and uses 1.08× the CPU under Starling than under GNOME — 6.33 s / 10.77 CPU-s against 5.71 s / 9.96. The cost is spread over every workload (1.04–1.13×) and concentrated in binary, at 1.31×.

Two things make that a floor rather than a ceiling. Ghostty’s GNOME grid was larger (47×201 against 45×201, 4.4% more cells), so the comparison is tilted against GNOME and it still won. And the CPU charged to Ghostty excludes whatever the compositor itself spends — this is what the client pays, not what the system pays. Starling asks about 10% more of a Wayland client than mutter does under this workload.

For TerminalApp the equivalent run is confounded: on Starling the GTK build is handed a 56×244 grid by the compositor (it sizes clients itself), against 47×201 on GNOME, so the two are not comparable directly. What it does show is that the GTK embedder costs TerminalApp little — 4.87 s / 8.62 CPU-s at 13,664 cells through GTK on Starling, against 4.51 s / 8.15 at 12,532 cells through the native DMA-BUF path on the same compositor: about 9% more cells for about 8% more wall time.

5 · Round 3 — Ghostty’s nightly, and the end of the lead

Rounds 1 and 2 measured ghostty 1.3.0~us1-0ubuntu1, the build in Ubuntu’s archive — dated 2025-12-16, seven and a half months old. In the meantime Ghostty’s maintainer announced large IO-throughput gains landing in libghostty. That makes the first two rounds a comparison against a stale opponent, so the nightly was built from the tip source tarball published the same day as this report (1.3.2-dev+48d85ea, Zig 0.16.0, ReleaseFast) — the same app runtime, renderer and event loop as the packaged build, so the only variable is the seven months of work.

The claim holds. On this machine the nightly takes the suite in 3.998 s against the shipped build’s 5.705 — 1.43× faster overall, and far more than that on individual workloads: alt_screen 4.7×, long_lines 3.8×, sgr_truecolor 2.0×, unicode 1.9×.

And it takes the lead from us. Against the nightly, TerminalApp is 1.13× slower on wall time (4.535 s vs 3.998) and ahead on exactly one workload of ten. CPU is close to parity — 7.39 CPU-s against 7.19, or 1.03× — so we are not paying more to lose; we are simply no longer faster.

Their three published tests, reproduced across five terminals

The announcement runs three tests: time cat 150MB_ascii.txt, time cat 150MB_unicode.txt, and DOOM-Fire-Zig. All three are below, on five terminals, all at 47×201, median of 3 runs. The corpora are not published so the two cat files are reconstructions of the same size and shape; absolute seconds therefore are not comparable to their machine, only the ordering and ratios measured here.

DOOM-Fire-Zig renders until a key is pressed and prints a running average to the screen. It was patched in two places (marked BENCH in src/main.zig) to stop after a fixed 600 frames and report on stderr — stdout, the byte stream the terminal actually renders, is unchanged, and every terminal is asked for exactly the same frame count, so fps is a clean function of how fast each drains and draws it.

The headline reproduces. Ghostty nightly is first on all three tests, and its margin over the older Ghostty is the size claimed: 2.24× on ASCII, 2.33× on Unicode, 1.95× on DOOM-Fire. On DOOM-Fire the published ordering reproduces exactly for the four terminals both runs share — nightly > Alacritty > Ghostty-old > Kitty — and our Ghostty 1.3.0 lands at 520 fps against their quoted 532 for 1.3.2, within 2%.

Two orderings differ from theirs, worth flagging rather than glossing: on ASCII we get Kitty ahead of Alacritty (1.250 s vs 1.354) where their table has the reverse, and our Kitty DOOM-Fire number (354 fps) is well below their 485. Different machine, different GPU, different corpus, and a fixed 47×201 grid rather than whatever window each opened with — any of which can move a single result. The claim being tested is Ghostty’s, and that one holds.

Where TerminalApp lands. Second on ASCII — within 14% of the nightly on wall while using the least CPU of any terminal here (1.11 against 1.47). Third on DOOM-Fire, ahead of both Kitty and the older Ghostty. But last on Unicode, behind even the 7-month-old Ghostty, at 2.3× the nightly and 1.4× Alacritty. That is the clearest signal in this table: our UTF-8 decode path is the weak point, not our ASCII path, and it matches unicode being one of our worst ratios in the main suite.

Why DOOM-Fire is slow for us — measured, not guessed

DOOM-Fire is an SGR torture test. Each cell is a 3-byte block glyph (U+2580) preceded by 256-colour foreground and background escapes whenever either changes, which in a fire animation is most cells: 13.5 bytes per cell against 3.0 for the glyph alone. A profile of TerminalApp during the run puts 21.4% of its time in Swift runtime bookkeeping — exclusivity checks 14.7%, ARC 4.6%, copy-on-write uniqueness 2.2% — against 17.4% in the emulator’s own parse-and-apply work, with _processCsi the single hottest symbol at 6.2%.

To separate the ingredients, the same program was rebuilt twice: once with the glyph changed to ASCII #, once with the colour escapes removed entirely. Same frame count, same cell count, same everything else. In TerminalApp:

Variant (600 frames, 56×244)fpsCPU-sKB/frameThroughput
UTF-8 glyph + SGR (upstream) 4583.05180.480.8 MB/s
ASCII glyph + SGR 4963.12154.875.0 MB/s
UTF-8 glyph, no SGR 30300.6340.3119.2 MB/s

It is not the Unicode. Swapping the 3-byte glyph for ASCII buys 8% — the escapes are what cost. And most of the raw fps difference is simply volume: the SGR stream is 4.5× more bytes per cell, so every terminal renders far fewer frames of it. Ghostty’s own fps drops 5.45× on the same comparison, close to our 6.6×.

The real gap shows only once you divide out the volume. Ghostty sustains ~148 MB/s whether the stream is plain glyphs or saturated with escapes — a 2.1% difference. TerminalApp does 119 MB/s on plain glyphs but 81 MB/s once escapes are in it, losing 32%. That is the defect: escape handling costs us a third of our throughput and costs Ghostty essentially nothing. The profile says where it goes — an escape returns the parser to ground state and breaks the printable-run fast path (a6e5042), which only fires on runs of consecutive plain ASCII in ground state. With an escape between cells every run collapses to length one, so each cell pays the per-write exclusivity and COW checks that the run path exists to amortise, plus the CSI parse itself.

Two consequences worth separating: we are also slower than Ghostty on the plain stream (119 vs 148 MB/s), which is a straightforward per-cell write cost; and we degrade on escapes where Ghostty does not, which is the fast-path collapse. The second is the larger and the more fixable.

How much is recoverable

Replaying the captured stream through the emulator alone — no Flutter, no compositor — isolates the core. There it runs at 122 MB/s, and a profile with rendering out of the picture puts 46.8% of its time in Swift runtime overhead: dynamic exclusivity checks 33.3%, ARC 7.4%, copy-on-write uniqueness 6.1%, against 43.2% doing the emulator’s own work. A C++ core covering the same hot path — flat array, per-character writes, no fast path — was written to bound the ceiling. Both count cell writes, and on this stream they agree to 54 writes in 3.81 million, so they are demonstrably doing the same work.

The two flag builds are not shipping proposals — they bound what a Swift-side restructure (a flat grid plus a buffer pointer held across the feed loop, so length-one runs stop re-paying exclusivity and COW) could recover: about 2×. Even with every safety check disabled Swift stays 2.7× behind C++, so the rest is not checks at all — it is [[TermCell]]’s double indirection and codegen.

Whether any of that reaches the user is a separate question, and a crude serial model of it gave the wrong answer. Measuring instead: the same captured stream was catted through the live app at a fixed grid, once normally and once with repaints suppressed (the repaint interval is a single constant), against the offline core on the same bytes and grid.

Rendering is not the bottleneck. Turning it off saves 0.73 CPU-seconds but only 0.05 s of wall — it is ~93% parallel with the parse, and costs 8% of the critical path. That path is 79% emulator core (0.510 s of 0.646 s), with ~0.084 s of PTY and everything else. So core work translates almost directly into user-visible time, and the earlier serial estimate — which had rendering absorbing a third of any gain — was wrong.

Holding the non-core 0.136 s fixed: a 2× Swift restructure lands at ~0.39 s (153 MB/s), roughly parity with Ghostty’s 0.384 s on this stream. A C core at 5.6× lands at ~0.23 s (263 MB/s), about 1.7× ahead of it. Those are projections from a measured decomposition rather than a guess, but they still assume the render tail stays parallel; it consumes 0.73 CPU-s today, and at a 0.23 s wall that is ~3 cores of a 16-thread part, so it should hold. The harness is in test/bench/core/.

On language: C and C++ measure the same here — 680 vs 670 MB/s on this stream, 1124 vs 1038 on the no-SGR one, with byte-identical checksums and cell-write counts. C is the better fit regardless, because it is what this repo already speaks: 42 .c files to one .cpp in the shell, and every SDK bridge target is C — including the one named FlutterSwiftBridgeCxx. One detail if it is ever wired in for real: Swift’s TermCell is size 13, stride 16, offsets 0/4/8/12, and CellAttrs.rawValue is a UInt8 — so the C struct must be { uint32_t scalar, fg, bg; uint8_t attrs; }, not a uint32_t field, or the two sides disagree about three bytes.

Not run, and why. iTerm2 and Terminal.app are macOS-only and cannot run on this machine at all. Warp is not in Ubuntu’s archive and its Linux build requires an account sign-in, so it was not installed. And there is no v1.3.2 tag in the Ghostty repository — the newest release tag is v1.3.1, and the nightly source self-reports 1.3.2-dev, so the announcement’s “1.3.2” is a main-branch development build that cannot be rebuilt from a released artifact. Ubuntu’s 1.3.0 stands in for it, and lands within 2% of their quoted 1.3.2 on the one test where a direct comparison is possible.

6 · The core, rewritten in C

The decomposition above said the emulator core was 79% of the critical path and that rendering was ~93% parallel with it, so core work should translate almost directly into user-visible time. It did. The parser, grid, scrollback and alternate screen now live in C (apps/TerminalApp/Sources/CStarlingTerm); the Swift side is a thin wrapper, and TerminalApp.swift did not change at all, because the wrapper keeps the same API and TermCell is laid out to match the C struct so cells cross the boundary without marshalling.

It is a port, not a rewrite of the behaviour, and that is checked rather than asserted. A differential harness runs both implementations over the same bytes and compares every cell of the grid and scrollback, the cursor, the modes and the emitted responses: identical on all ten benchmark workloads, on a hand-written edge-case stream at six grids (5×3 up to 244×56) and five chunk sizes (1 byte to 64 KB, so multi-byte characters split across feeds), and on 200 randomised streams of escape soup, invalid UTF-8 and OSC variants. All of it in test/bench/core/.

Live, on the Starling session, the same captured DOOM stream went from 92 to 250 MB/s on 2.8× less CPU — ahead of the 221 MB/s the decomposition predicted. The core alone is 1.1× to 5.1× faster per workload, with the largest gains where the escapes are (unicode 5.1×, sgr_fg 4.2×, binary now 3.7× ahead of Ghostty rather than behind it).

Where it now loses is informative. Ghostty still leads on alt_screen (1.45×), long_lines (1.39×), scroll_region (1.21×) and the two cell-filling workloads — every one of them dominated by moving or blanking whole rows. The Swift version handed out a single shared blank row by copy-on-write, so a row that scrolled past untouched cost a retain; the C port fills each one with a memcpy from a template instead. Restoring that looked like the obvious next move, so it was built — refcounted shared rows, differential-clean and ASan-clean — and measured worse: 1–5% where it was meant to help, and 23–28% slower on the hot path, because put_scalar then tests the shared flag on every character while the run fast path pays it once per run. Reverted. The arithmetic points somewhere else: scroll_region’s ~600k line feeds each memmove ~47 Row structs, ~450 MB in total, which at ~20 GB/s is ~22 ms of its ~77 ms — the 29.6% the profile attributes to memmove. If that holds, the fix is a row-offset ring for the grid, not shared cells.

One more thing the rewrite settled: the memory leak is not in the emulator. RSS still climbs 276 → 335 → 386 MB across three suites with an emulator that shares no code with the one that leaked before. Whatever holds those 25 MB per styled dump is on the Swift or engine side of the boundary.

7 · Memory: the one place Ghostty wins outright

Resident set after each successive suite tells two different stories. Ghostty finishes every suite at essentially the same number — 159, 160, 160 MB — having drained 419 MB of output three times over. TerminalApp finishes at 208, 269, and 331 MB: +61 MB for each suite it runs, with no sign of levelling off.

Round 2 rules out the desktop and the embedder as causes. The GTK build on GNOME grows 278 → 338 → 395 MB (+59 MB per suite), and the same GTK build on Starling 304 → 374 → 444 (+70 MB). Ghostty sits at 161 MB on GNOME exactly as it sits at 160 on Starling. The growth follows our code, not the compositor and not the embedder.

Running the suite once with an RSS sample after every individual workload localises the growth: of the 93 MB a single pass adds, sgr_fg contributes 43 MB and sgr_truecolor 27 MB. The other eight workloads together account for 24 MB, most of it first-touch warmup in the first two. Five seconds of idle afterwards releases none of it.

That points at styled content, so the discriminating test is to run one styled workload over and over. If the growth were a high-water mark, RSS would jump once and then flatten. It does not.

Two obvious suspects are ruled out by reading the code. Scrollback is bounded — it is cut back to scrollbackLimit (2,000 rows, plus 512 of slack) in TerminalEmulator.swift:662, which at this grid caps it near 10 MB. And the TextStyle cache added in round 2 is bounded too: it is dropped wholesale once it passes 4,096 entries TerminalApp.swift:652, precisely so truecolor content cannot mint an entry per cell. Neither can hold 25 MB per pass, and sgr_fg only uses eight distinct colours in any case.

So the retention is somewhere else — the per-row widget tree, the framework’s text layout objects, or engine-side caches inside the app process. Pinning it down needs a heap profile rather than a reading, which is outside what this benchmark can answer. It is the clearest open defect the suite found, and it is worth noting that a long-lived terminal is exactly the kind of process where 25 MB per styled dump compounds.

8 · Idle

With both windows open and static, sampled over 20 s: TerminalApp costs 0.01 CPU-s (0.05% of a core), Ghostty 0.09 CPU-s (0.45%). Both are negligible in absolute terms; the 9× ratio between them is real but worth nothing on a desktop. Neither terminal spins when nothing is happening.

10 · Method, and what this does not measure

  • Which Ghostty you measure decides the answer. The distribution build (1.3.0~us1-0ubuntu1, Ubuntu resolute/universe, binary dated 2025-12-16) and the nightly built from the same day’s tip tarball differ by 1.43× on this suite — a bigger gap than the one between either of them and TerminalApp. A benchmark against “Ghostty” that does not name the build is not reporting much. Both are ReleaseFast, GTK runtime, OpenGL renderer, io_uring; only the source differs.
  • Each terminal’s own process only. CPU is read from /proc/<pid>/stat, which aggregates every thread of the process (Ghostty runs 29). Compositing is excluded on both sides — the frames each app submits are drawn by DesktopShellApp, whose cost appears in neither column. If one terminal submitted many more frames than the other, that difference would be invisible here.
  • Round 1’s grid asymmetry favoured Ghostty (12,532 cells against 9,045); Round 2 removes it entirely (47×201 both). Where the two rounds disagree, Round 2 is the one to believe — and it moved results in both directions, which is the sign the asymmetry was doing real work rather than just flattering one side.
  • Round 2 drives the suite without synthetic input. The runner is launched as the terminal’s own child — ghostty -e on one side, STARLING_DEV_SHELL (an existing hook) on the other — and it finds the terminal by walking up its own process tree, recording the pid and grid it attributed to a meta-*.txt beside the results. Neither terminal was typed into, so nothing depends on a keystroke landing in the right window.
  • The two TerminalApp builds are not the same binary. Round 1 uses the DMA-BUF child path; Round 2 the GTK embedder. That is why the compositor comparison in §4 leans on Ghostty, which is one binary on both desktops. Comparing TerminalApp’s own two rounds conflates embedder with compositor, and the grids differ too.
  • One machine, one afternoon. Within each round the two terminals ran minutes apart on an otherwise idle machine (load average 0.2), one at a time, never concurrently; the two rounds are about half an hour apart, separated by a session switch. Numbers are only comparable within one sitting on one machine, which is why the corpus, the runner and the probes are checked in rather than described.
  • Font coverage differs and is not a performance question, but it does mean the two unicode runs do not put identical glyph loads on the rasterisers: CJK, box-drawing and emoji are blank in RobotoMono, which TerminalApp bundles. Decoding — the thing that workload targets — is unaffected.
  • Not measured: startup time, latency under interactive input, memory under normal (non-benchmark) use, and anything requiring a GPU-side counter.

Measured 2026-08-04 on starling-dev by test/bench/run-bench.sh; the two memory probes (rss-probe.sh, repeat-probe.sh) and the summariser (analyse.py) sit beside this report, with the raw per-run outputs in data/. All runs are reported, including the unfavourable ones.
