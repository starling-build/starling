# amd-opus SPEC: a paragraph parts around a picture in mid-page (compat 15 first, then c14)

Design only, no code. For whoever takes amd-3's OPEN item 1 (board 20261120-123837-amd-3).
Lab prints: /data/s/amd-3/lab/pic-wrap/word-win (generator mk.py, compare cmp4.py).

## 1. What Word does (measured on amd-3's prints)
Picture 509 pt wide, from the margin, top 172.0, foot 284.4, distT = distB = 0. Item 2's first line box starts at 158.9; pitch 13.32 (single 11.58 at a multiple of 1.15).
- c15, square and top-and-bottom alike: line 1 stays at baseline 168.3; line 2 at 293.8 = foot 284.4 + 9.4 (the line's top-to-baseline); line 3 at 307.1. Same line breaks as without the picture.
- c14: line 1 goes to 293.8, the others follow it.
- tb w300 (foot 238.2): c15 line 2 at 247.6 = 238.2 + 9.4. Again just the foot, no step, no space before.
- So Word works LINE BY LINE: a line that meets a picture with no room beside it goes to the picture's foot, and the paragraph's later lines follow it. c14 and c15 differ only in how much of the line counts. In c15 only the text counts (11.58: 158.9 to 170.5, clear of 172.0). In c14 the whole line counts (13.32 reaches 172.2 and meets the picture by 0.2).
- NOT proven by these prints, because the picture always meets line 1: whether c14 also parts when line 1 is clearly clear, so the `reachAll` "c14 goes under whole" rule (Paginate ~4520) may be wrong; whether the text-only test holds for lines 2.. in c15; and how widow control behaves (the lab has no styles part, so its widow setting is Word's default). Lab L1/L2 below settle these before any code.
- Same family: 9bde52 (`meets` in the anchor run, word-rules.md:421) already measures an anchor line by its text alone. At the PAGE FOOT Word counts the whole line (lenovo-5 footfit, word-rules.md:475). So the text-only test is for pictures only, never the foot.

## 2. Where the split happens
In `_paginate`'s per-paragraph loop `while cursor < bottom` (Paginate ~5122), not in `_layoutParagraph`. The engine already parts a paragraph in mid-page for floating tables: `floatHold = (limit, back)` (~5065). The cut takes the lines that fit above `limit`, adds that piece, then sets `y = back` and goes on (~5381). Generalise that one mechanism. Do not add a second one.
1. Make the hold a small struct `{limit, back, source: .table | .picture, measure: .whole | .text}`. The floating-table use becomes `source: .table, measure: .whole`, with unchanged behaviour (lab764 and the 136.7 case must not move).
2. At the start of each piece (first piece, and after every hold), look for the first band under `y` that the piece's remaining lines reach and that `noRoom` reports blocks the line (top-and-bottom, or square leaving less than `em`). Bands are the existing `bands + fixedBands`. Set the hold to `limit = band.top` (distT included, as bands already are) and `back = band.bottom` (distB included). A band whose top is above `y + first line's measure` is NOT a hold: the existing start-of-paragraph pushes (t3d step, list-label step, plain `reach`, ~4490-4590) keep deciding line 1. The hold only parts lines 2.. away.
3. The fit test against a picture hold: c15 counts the line without its multiple's extra (`lineHeight / lineSpacing` for a multiple with no exact height, the same as `meets`); c14 counts the whole line. Exact and at-least lines: whole line for now (lo-717ff943's at-least rule already tests text extent beside boxes; lab L4 checks it here).
4. If no line fits above the limit, the piece starts at `back` (today's push). If some fit, add the piece, set `y = back`, and loop: a second picture lower down gets a second hold. Keep `guardSteps`.
5. If `back` is past the page foot, the rest parts to the next page through the normal `newPage()` route, with ordinary page rules.
6. Scope of v1: body paragraphs only (`_cells[i] == nil`), with text, and pictures NOT anchored in this paragraph from "paragraph" (those move with it; the existing own-box rules stay). That means pictures fixed from the page or margin, or anchored in an earlier paragraph. Multi-column: lo-eb12e7d4's rule (a line meeting a top-and-bottom band in a column that is not the last goes to the next column, ~4606) stays ahead of the hold.

## 3. How the line boxes cross the picture
- The painter's lines stay contiguous in flow coordinates. Nothing in `_layoutParagraph` changes for v1. The jump lives only in the page map: two `PagePiece`s of the same paragraph on the same page, `[top, cut)` at `pageY = y` and `[cut, bottom)` at `pageY = back`. The carried line's top is exactly `back`: no space before is set again, and there is no grid or line step (Word's 293.8 and 247.6).
- Audit every reader that assumes one piece per paragraph per page before turning it on: anchor-run `lineTop` (`_pages[page].last(where:)`, ~4807); `flowPoint`, `canvasPosition`, caret and selection rects; `lineDump` and `pageNumber(ofParagraph:)`; paint of paragraph borders and shading (Word: unknown; lab L4 adds a bordered and a shaded item); list labels and the paragraph's own float anchors (both on the FIRST piece only); and `_tops`/`_heights` users that compute "where the paragraph ends" (`top + _heights[i]` is now short by the jump, so record `_holdJump[i]` and add it there).
- Line widths: v1 keeps the breaks the paragraph had. That is right when the carried lines are full width under the picture, which is every case in amd-3's lab. If the carried lines would stand beside ANOTHER square picture (a strip), they must be laid out again with the jump. Add `_lineDrop[i] = (fromLine, dy)`, which the beside-indent loop in `_layoutParagraph` (~1600, the `bottoms[k]`) adds to lines `>= fromLine`, and re-run like `_besidePending`. Until that exists, fall back to today's whole push in that case and leave a RuleTrace so the docs show up.

## 4. Interactions
- Widow and orphan control: a picture hold is not a page break. Word leaves ONE line of item 2 above the picture. So the hold skips the widow and orphan logic, as `floatHold` already does (`floatHold == nil` guard, ~5292); L2 confirms with widowControl set on explicitly. At a later PAGE part of the same paragraph, widow counting must count all its lines on this page, the ones above the picture included. Today `first` is taken from `cursor`, which would see only the lines under the picture.
- keepLines: unknown whether Word still parts a keepLines paragraph around a picture on the same page (likely yes: it is not a page part). L2 decides. Until then keepLines means no hold (today's behaviour).
- keepNext and every "does it fit on this page" check made BEFORE placing (keepNext chain ~4172, keepLines, the column checks): measure the paragraph with its jump. Put the band search in one function `holdJump(i, at: y) -> Double`, used both by the placement and by those checks, so they cannot disagree.
- Tables: a table row that meets a picture keeps today's whole-row behaviour (a table does not wrap). A table after a parted paragraph starts after its last carried line, through `_holdJump`. Text inside cells: out of scope; it needs its own lab.
- Floating tables: the same struct (step 2.1), so no behaviour change, and one code path to review.
