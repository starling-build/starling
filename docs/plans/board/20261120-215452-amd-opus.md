# amd-opus RULE (puzzle 9, 2026-11-20): sa2 78bf1be7, Calibri italic beside Tahoma. Word counts EVERY run; our engine drops it in two places

For amd-3 (wip/amd-3-mixed-generic, 17402a9ab).

## What Word does (from the doc's own Word print)
- Every line holding Calibri and Tahoma runs is Tahoma's ascent (11.0) over Calibri's descent (2.95) at 11 pt, times the multiple. That includes lines whose Tahoma part is only punctuation or digits:
  - "Acadêmico; " (para 23, 1.05 lines; the only Tahoma run is ";"): Word's pitch is 14.52. Every run counted gives 14.66; ";" not counted gives 14.13.
  - The list lines "Contrato (Número/Ano): 2/2014;" etc. (single, before 0.65): Word's pitches are 14.54, 14.64 and 14.52. Counted, 14.61 and 14.56.
- All mixed pitches in the doc fit "every Latin run counts" within ±0.15 pt, which is the scatter of plain Tahoma pitches too (14.54 to 14.67 at 1.1).
- So there is no property to find on Word's side: font slot, rFonts hint and neutral characters do not matter here. The 21 of 50 came from two engine gaps.

## Gap 1: the paragraph strut overrides the mixed rule
`_strut` (RichLayout+Lines.swift) builds a forced strut from the "held" run. In paras 17, 23 and 32 to 36 that is the Calibri run: height 1.231 (the mixed rule's `nat*mult*lineSize/size`, where 1/1.05 for w:w cancels the 1.05 multiple) at the w:w size of 11.55 pt. That gives 14.22 pt lines, where Word's are 14.64. The run overrides (asc 1.0005 em, desc up to 0.330 em) are right, but `forceStrutHeight` throws them away. Para 25 had no strut, so it was already right.
- Fix tested: when the held run carries the mixed rule's ascent and descent, `_strut` returns nil, as it already does for Kokila and ruby lines. I tagged the run with a debugLabel suffix " mixed-latin-line" in the rule and checked it in `_strut`.

## Gap 2: runs containing the "ﬁ" ligature (U+FB01) escape the rule
The per-run guard `allSatisfy { $0.value < 0x250 }` skips "conﬁrme", "conﬁrmá-la", "conﬁrmar" and "conﬁrmação". The doc types the ligature character itself. Those runs keep the engine's own Tahoma box, split evenly (ascent 11.9). So the Tahoma + Lucida lines of paras 38 and 52 come out 15.5 pt, where Word's are 14.6. That is the over-count that looked like "all runs counting is wrong".
- Fix tested: also accept U+FB00..FB06 (Latin ligatures, which take the run's ascii/hAnsi face). By property, the guard should be "characters set in the ascii/hAnsi slot", not a code point limit.
