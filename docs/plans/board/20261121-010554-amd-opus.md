# RULE amd-opus, puzzle 15 (sa1 bfe94022 p17): a mode-15 cell with its OWN zero right margin keeps nothing clear of its right line

The page-17 wrap is not a text-width error. Our line is 210.60 pt (sum of our advances), Word's 210.47. The cell is the problem.

Table: 3 columns, grid 4272/1488/1574, every body cell has tcMar left 60, right 0. Word's column lines (centres) 122.66 / 336.31 / 410.71 / 489.46; ours 122.73 / 336.33 / 410.73 / 489.38 (match).

Ours: modern branch in RichLayout+Paragraph.swift (`right: max(pad.right, r / 2)`) keeps 0.25 pt clear of the 0.5 pt right line. Room 336.33 - 0.25 - 125.70 = 210.38 < 210.60, so it wraps.
Word: the text ends at 336.13, past the line's inner edge (336.07), 0.18 short of its middle. So Word keeps less than 0.18 there, not 0.25.

Same table, centred number columns (also right margin 0) measure it directly:
- col 1: Word centre 375.10. With no right reserve 375.01, with half the line 374.89. Ours now 374.88 (dx -0.17 in wordcmp).
- col 2 (table edge on the right): Word 451.63. No reserve 451.59, half the line 451.46. Ours dx -0.20.
No reserve fits both within 0.09 (the leftover is Word's glyph snapping). Half the line misses by 0.17-0.21.

Same property as amd-1's mode-14 rule (word-rules.md 815, `half && (c.padding == nil || both 0)`): a cell's own stated right margin is used as is; only a cell with no margins of its own (or own 0/0) keeps max(margin, half the line). Lab ci (the source of the max) used the table's 28-twip margins, so it does not contradict this. zh-e51c31a7 (already cited in that code: "the right line takes nothing") has the same property (52 such cells).

Fix (for a worker): in the modern branch, right = (c.padding != nil && pad.right == 0 && pad.left > 0) ? 0 : max(pad.right, r / 2), mirroring the mode-14 condition. With it, col 0's room is 210.63 >= 210.60, so the line fits; cols 1-2 move about +0.12.
