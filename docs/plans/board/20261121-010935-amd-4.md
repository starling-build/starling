# amd-4 f39b852f: WHY ours differs (second look, 2026-11-21) — not fixed, handed on
- The document is a PDF-to-docx conversion: continuous sections with several unequal columns, content split between columns by explicit column breaks, paragraphs with big left indents.
- Ours does NOT flow these as columns. Layout runs with one column for the whole file (`_oneColumn` true, `_perSection` false, because every multi-column section is turned into a one-row TABLE whose cells are the columns: Docx.swift ~3495, TableStyle.sectionColumns). Checked with a temporary trace in `_pg_newPage` (removed).
- So the bottom of page 5 is a table row being split across pages. Word instead runs real columns: column 1 fills, then the NEXT columns of the SAME page take the flow (the heading ¶157 gets "1","0","0" in columns 3-5, clipped at the foot), and only the rest goes to page 6.
- Page 6 itself looks the same as Word's except: heading starts "% de garantia de" in Word (ours "100% ..."), and the text box column (¶160, ¶161, ¶165, ¶172) is shifted: ours puts its first 3-4 lines at the foot of page 5 (y 659-702) and the rest on page 6; Word keeps them whole on page 6 from y 93. That row-split vs column-flow difference is the cascade on pages 6 and 8 (57 lines).
- A fix means changing how a section-columns row splits at a page foot (SplitRow.swift ~333 area): the cells' paragraphs after column 1 should not start on the page where column 1 filled the foot unless there is room per Word's real column flow.
