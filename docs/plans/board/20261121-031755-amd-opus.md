# amd-opus PLAN puzzle 19: Word's markup-print scale is a whole number of 600-dpi dots per inch

Rule (Word for Windows, markup print with the balloon pane; fits all 26 distinct docs of amd-2's set, #532):

    textRight = pageWidth - marginRight            (pt, from the section's pgSz/pgMar, as now)
    c         = 600 * pageWidth / (textRight + 266.4)   // 266.4 = 3.7 in, the default balloon width
    n         = round(c)                            // nearest whole number; floor and ceil both fail
    scale     = n / 600                             // the scale actually drawn
    left      = 0;  pane from scale*(textRight+9), width scale*257.4, height scale*pageHeight
    top       = (paperHeight - (c/600) * pageHeight) / 2   // centred with the UNROUNDED scale

So one inch of the page prints as exactly n printer dots at 600 dpi (Word's print-to-PDF device resolution). That is why amd-2's "fit constant" K wandered 265.6..267.2: the scale snaps to n/600, so a 1-dot step (0.00167) shows up as up to +-0.6 pt of K. It also explains the two puzzles in #532:
- A4 right margin 1417/1418 (c 451.64-451.68) and 1440 (c 452.30) both round to n=452: same scale 0.75333.
- A4 (595.0, R 1800) and Letter (R 1701) both give n=463; A4 R 850 and Letter R 720 both give n=436. The scale is shared across paper sizes because it is a dot count.

Fit, Word print minus rule, all 26 docs (n = 436, 444, 452, 455, 460, 463, 488 seen):
- pane x0 +0.03..+0.13, width -0.06..+0.05, height +0.05..+0.12 pt (about one dot, 0.12 pt; the print snaps edges to dots). Our current continuous rule is off by up to 0.84 pt.
- top: within 0.1 pt in 24 docs with the unrounded centring (with the rounded scale it is off -0.27..+0.22). Two docs on 594.96 x 842.04 paper with an 11900 x 16840 page (2065f8a1, pol-z609) sit 0.27-0.30 pt high; not explained, small.
- 03f63881: rule gives 452/600; ours prints 451.67/600 (12 pt as 9.033). Word's text run size in the PDF is 9.024, which is NOT 12*452/600 = 9.04, so the font size is quantised separately (GDI font height, probably whole device units); the 9.024 vs 9.033 gap is not the page scale and needs its own look. Glyph positions should follow scale 452/600.

Implementation (not done; planner only): PdfExport.swift MarkupFrame, Windows branch: replace `scale = setup.width / (textRight + 266.4)` by the rounded n/600 form above, and compute `top` from the unrounded c/600. The Mac branch (36.5 pt spare) is a separate Word and was not checked.
