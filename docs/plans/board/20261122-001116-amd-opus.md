# amd-opus SPEC ja 7c77f08b: Meiryo UI 「 and ・ overprint the next kanji. Cause: the stand-in's full-em glyph is drawn in a half-em cell. Fix: the font's `halt` feature (for amd-9)

SHORT: the widths are right; only the ink is drawn in the wrong place. Turn on the stand-in's half-width feature (`halt`) for a CJK mark we set at about half an em, and measure its width with the feature on. Patch: /data/s/amd-opus/starling/lab/meiryo-halt.patch (10 lines). The p1 title then looks like PowerPoint's print.

## Cause, by property
- Our pen positions already equal PowerPoint's (p1 title, 32 pt bold: 「 113.4, 貯 129.4, ・ 214.8, 増 231.4 in both). The advance is right.
- These marks do NOT go down the East Asian path in Slides. They are set as Latin: Meiryo UI's width table (0.5 em), stand-in
  Liberation Sans. The engine then falls back to Noto Sans CJK JP to draw them. So any fix in the `ea` block never runs (amd-9's try 1).
- Noto Sans CJK JP draws 「 （ 【 as a full em with the ink on the right (「 ink 0.64-0.97 em) and ・ centred at 0.5 em.
  We give the full-em glyph a half-em cell by negative letter spacing AFTER it, so its ink lands on the next character.
- Meiryo UI's own glyphs for these are half-width (opening marks have their ink on the left of the half cell; ・ is centred).
- Noto has that exact form: its `halt` feature (GPOS) gives 「 （ 【 placement -0.5 em, advance -0.5 em; ・ placement -0.25 em,
  advance -0.5 em; 」 、 。 placement 0, advance -0.5 em. The engine applies it to the fallback face (measured: 「 at 32 pt is
  16.0 pt with `halt`, 32.0 without). amd-9's try 3 had no effect for the reason above: it was not on the path that sets the mark.
- Ruled out: the advance (already right); `palt` (gives Noto's own proportional widths, not the original's); punctuation-width
  rules (the widths are not in question); lenovo-3's East Asian face fallback (not on this path).

## Rule
In the per-character branch that applies a width correction by letter spacing (RichLayout+Span+StyledSblk4.swift, the final
`else` with `var spacing = (s.letterSpacing ?? 0) + extra`): when the character is in U+3000..U+FF5F, the correction narrows it,
the stand-in's glyph is about a full em (> 0.9 em) and the target is under 0.6 em, set it with `FontFeature("halt", 1)` and take
the width correction against the `halt` width (extra += full - halt width), so the advance does not change.
- Horizontal text only. Vertical marks have their own path (`vert`); do not add `halt` there.
- The glyph-width cache in RichLayout+Lines.swift `_glyphWidth` keys every feature list as "|f", so a `halt` width and a
  `kern 0` width of the same face, size and character collide. Key on the features' tags and values (in the patch).

## Expected effect
- No line breaks change: the advance is the same. The text layer's x for 「 moves (our PDF reports the drawn origin, 97.4
  against PowerPoint's 113.4); the visible page matches. Check the visible page, not the text layer.
- Affects every face whose CJK marks we narrow by a width table while the engine draws them from Noto CJK (Meiryo UI, MS PGothic,
  MS UI Gothic and others in SlideEastAsianWidths). The branch is shared with Word: run the render gate (it covers Word) and the
  ja/zh/ko Slides sets, then crop a few titles with 「 ・ （ in ja decks to confirm.
