# amd-perf HANDOFF: render-gate profile (2026-11-22)

Four recent runs, from the run logs and the gate script. Setup is negligible (base binary and base rows are cached).
Serial chain per run: PR build 87-192 s, then Word compare 43-74 s and Slides gate 132-164 s run side by side (already parallel). Total about 4-6 min of work; queue wait (8-9 min median) is bigger than the work.

Findings:
1. The build is the only serial step and it is the one that swells under load: load average was about 260 on 192 cores (6 runners, each -j 30 build plus 32-44 render jobs). A one-file edit alone takes 34-69 s on a quiet box: compile one file, "Emitting module OfficeApp" (single-threaded, does not shrink with -j), link about 3 s.
2. Slides gate (600 decks) always runs except Word-reader-only changes. It is the longest of the two parallel steps, so it sets the finish time.
3. /data hit 100% full during this work (builds fail with "database or disk is full"). Scratch per session is the cause: a full disk turns into false BUILD FAILED runs.

Proposals (not landed, each changes gate semantics or needs the coordinator):
A. Stagger: cap concurrent builds to 3 across runners with a shared lock (builds are the part that scales badly with oversubscription; render jobs are cheap). Expected: build back to 60-90 s, and fewer runs timing out.
B. Start the Slides gate decks as soon as the binary links, not after the Word pair is staged (check ordering at render-gate.sh lines 179-190).
C. Disk: a cron that prunes /data/s/*/ scratch older than 2 days, alert at 90%.
