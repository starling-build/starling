## The rule (decks with no drawing part, `render(word: false)`)

PowerPoint tries whole point sizes from primFontSz (65) down to the rule's floor (5), one size for every parTx (they share
the constraint), and keeps the LARGEST size where all of these hold:

1. Every word of every node fits the box width on its own (no word is ever broken), measured as the Slides line fit measures
   (each advance rounded to 1/8 pt, ties up, plus the unrounded Calibri pairs: kern="1200" in this deck's default text style,
   so 12 pt and up is kerned). Words wrap greedily at spaces.
2. Box height. The size-tied height is h0 = s mm (the `h = primFontSz` constraint: 2.835 x s pt). The text needs
   need = lines x 1.0986 s + 1.6 s pt (line pitch = Calibri's 1.2207 x lnSpc 90%; tMarg = bMarg = 0.8 s pt; lMarg = rMarg = 0).
   - need <= h0: the box stays h0 (short text: 1 line at 50 pt in a 141.7 pt box).
   - need > h0: the box grows to need (rule h INF), but only up to the node's `h lte userT` bound
     (userT = 0.2 x dummy w = 0.2 x frame width: 112.64 wide, 72.0 narrow). Over the bound, the size fails.
     The bound limits only growth: h0 above it is fine (short text h0 141.7 > 112.64).
   - All parTx get the tallest node's height (`op="equ"`).
3. The row fits the frame: backgroundArrow is 2 x that height, so 2h <= frame height (this is what stops short text at 50,
   at 25 for frame 141.7 and at 58 for 330.7; it already works).

Each part is needed. Without the userT bound the long sizes come out 37/37/33/24 (PowerPoint 32/20/29/18).
With a 1.2207 pitch (Word's) they come out 27/17/21/13 for 29/18/23/14. Unkerned, 32 and 23 drop to 31 and 22.
Tightest cases: n3 narrow at 19 needs 72.14 against 72.0 (rejected), n5 wide at 23 needs 112.605 against 112.64 (kept).
So no tolerance; do not add one.

Siblings: no separate shrink order. One size for all nodes, set by the worst node (n2 narrow: "Plan the work" alone
would be larger, both print 20).

## Slide 28 (layout with the linV `w` rule removed): PowerPoint 5 pt, ours 39

Rules run in the order listed, each as far as it must go. Here the row is too wide whatever the size (linV w = frame w, it
does not depend on the font), so the primFontSz rule runs all the way to its floor: 5 pt. The row is still too wide, so
the lin algorithm then scales its children ALONG ITS DIRECTION ONLY, to fill the width:
- scale = frame w / (padding1 + n x linV + (n-1) x space + padding2) = 563.2 / 2016.0 = 0.2794
  (no space after the last node; padding2 = userP = 0.25 x dummy h = 56.32).
- Boxes print 157.30 wide (563.2 x 0.2794), x at 102.19, 290.95, 479.70 (pitch 1.2 x 157.3), padding1 12.59.
- Heights are NOT scaled: boxes 14.17 (5 mm), arrow 28.35. The arrow, negArrow and padding2 scale along too: the arrow is
  157.3 wide at x 495.4 (right end, after the -w negArrow), centred vertically as usual.
Ours: `render` keeps no size when none fits ("scaled as before") and `fit(_:into:)` scales the whole tree evenly, and the
text is fitted to its box from the cap: 39 pt. Fix: when no size fits and the layout has a primFontSz rule, use the floor;
then scale a lin row that overflows along its direction only. CHECK the decks the old "scaled as before" branch serves
(the org chart the comment names is defined at 10 x the frame and needs the even scale): keep the even scale for a tree
that overflows in both directions, or for one with no primFontSz rule.
