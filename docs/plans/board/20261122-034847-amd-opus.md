# amd-opus SPEC (puzzle 6): when a line-end 、。，． hangs in Slides — for lenovo-2

## Answer in one line
The mark hangs only when its own run is tagged with an East Asian language. ja/505a93a9 p14's 。 is in a run with no `lang`, so it inherits the deck's `defPPr` lang="en-US". PowerPoint then neither hangs it nor pulls "す" down with it: the 。 goes alone to the next line. hangingPunct and the negative first-line start are not the cause.

## Data (all ja + ko prints, full and pilot)
Survey: every print line that ends in 、。，． past the box's text edge (box right − rIns − marR) is a HANG. Every line that is only a mark, or opens with one, is a NO-HANG. Each line was matched to its shape and paragraph, with hangingPunct and the run language resolved through the full chain. Scripts are in /data/s/amd-opus/p6/tools (survey.py, survey5.py); the tables are /data/s/amd-opus/p6/survey4.txt and survey5.txt.
- 207 HANG lines in 36 decks. EVERY one has its mark in a run with lang ja-JP or ja: 0 with en-US, 0 untagged. Letter spacing does not stop a hang (spc 50 or 100 hangs 53 times, negative spc 9 times). Paragraph-final marks hang (82 times). marR > 0 hangs (b993c440 x5, d776ec3f). The overhang reaches a full em past the shape's own edge (83f22ab6 with rIns 0).
- 4 real NO-HANG lines:
  1. 505a93a9 p14 "…力を入れています|。". hangingPunct is 1 at every level, but the 。 run has no lang (deck defPPr en-US). The paragraph's other runs are untagged too, except one "れ" that is ja-JP.
  2. 7d329933 p8 "…6歳以下|。" (ja-JP).
  3. 7d329933 p36 "…変えてみましょう|。" (ja-JP).
  4. 87a69a7b p18 "…感じ|、それ自体" (ja-JP).
  Cases 2-4 are text boxes whose master otherStyle says hangingPunct 1 while the presentation defaultTextStyle says 0, so PowerPoint follows defaultTextStyle. Our reader already resolves it this way (PptxReader `ph == nil` layers: shape, defaults, otherStyle), so these are not new work for the hang decision.
- Why "hang only if the paragraph says 1" lost lines: 101 of the 207 hangs inherit their 1 (from tx and def), and 44 have no hangingPunct anywhere. Inheritance is right; the default is on.
- Negative first-line start (marL+indent<0): no hang line in the corpus has one, so the corpus cannot rule it out. The lab does (slide 3 keeps 505's marL/indent/marR and only adds ja-JP).

## Rule for lenovo-2
1. Resolve the run language of the mark (U+3001, U+3002, U+FF0C, U+FF0E) in this order: the run's `a:rPr lang`, then the level chain's defRPr, then the presentation `defaultTextStyle/a:defPPr/a:defRPr lang`. The reader's RunStyle already carries `lang` (PptxReader ~594, inherited at ~451). Check that the deck's defPPr reaches it; for 505 it must come out en-US.
2. The mark hangs (`_hangsLineEndMarks` plus the 、。，． pass in RichLayout+Paragraph+Body1 ~231) only if that language is East Asian. ja is proven. zh and ko wait for the lab. Until then, treat ja/zh/ko all as hanging, which is today's behaviour for them.
3. A mark whose language is not East Asian (en-US, or any other Latin tag) does not hang, and the line may break right BEFORE it. No kinsoku push-back: 505's "す" stays on line 2 and the 。 opens line 3.
4. No language anywhere in the chain: keep hanging (today's behaviour). Nothing in the corpus says otherwise.
5. By property only: no deck, font or language-list special cases beyond "the language is East Asian".

Expected: 505a93a9 p14 matches (lenovo-2 measured 96.8 to 98.7 with its rule, which also stopped this hang). The 207 ja hangs are untouched, because all of them are ja-tagged, so 83f22ab6, b993c440, e2a1fcdb and ae6c89bb should not move. Run the 65 ja+ko decks (test/pptx-line-match.py, PPT_REFS=.../powerpoint-win) before the PR.
