# amd-opus SPEC (Slides puzzle 9), 2026-11-22: simulated bold advance, Latin and East Asian, for lenovo-3 or amd-5

Labs read: lenovo-3 kanji-adv + kanji-adv2 (/data/s/lenovo-3/lab/kanji-adv), amd-5 clbold (/data/s/amd-5/lab/clbold), amd-1 gulim-fit
(/data/s/amd-1/starling/lab/gulim-fit). New lab sbold built (/data/s/amd-opus/starling/lab/sbold, sent to starling-bd for printing).
Readers: /data/s/amd-opus/p9/tab.py (mean advance per run), fit.py (scores the rules below).

## What PowerPoint does (all labs agree)

1. Paint, every face without a bold cut: the regular outline, text render mode 2 (fill + stroke), line width = font size / 35
   (0.34354 at 12.024, 0.51429 at 18, 0.91611 at 32.064). The bold run's Tf is sometimes 0.024 pt larger than the regular's: PDF writer, ignore.
2. Print offset: every kanji advance prints 0.024 pt (1/3000 in) past its layout value, regular and bold. That is the PDF writer.
   Do not add it to layout widths (puzzle 4: never take layout widths from print spacing).
3. Rule A, Japanese faces (MS Gothic and MS PGothic, 256 units per em; HG Maru Gothic M-PRO, 2048), measured in ja-JP runs only:
   bold advance = (the glyph's design units + 1) x size / unitsPerEm, then the usual rounding to 1/8 pt, half up (puzzle 4).
   - kanji-adv2, 90 bold runs, 13 to 32 pt, 3 faces: every run within 0.05 pt of the rule (an eighth is 0.125).
     "Bold = regular" misses 44 of 90 by up to 0.15. "x 0.983" (what we do for these faces' kana and Latin) misses all 90, by 0.42 on average.
   - It explains every oddity in lenovo-3's data. MS Gothic widens from 16 pt on and not below: 1/256 em at 16 pt is 1/16 pt, exactly
     half an eighth, so from 16 pt the extra unit rounds up one eighth, below it rounds away. HG barely widens: 1/2048 em is under 0.016 pt,
     so it shows only where the size sits just under a half eighth: 18.81 pt is 150.48 eighths, plus the unit 150.55, so 151 = 18.875
     (the pilot d776ec3f line's "18.93" is 18.875 + the 0.024 print offset + noise). MS Gothic at 18.84, 18.96 and 21.6 does not widen
     because the unit crosses no boundary there.
   - Kana too: MS PGothic kana in kanji-adv print 0.12 wider in bold at 24 pt, not 1.7% narrower.
4. Rule B, Gulim (1024 units, ko-KR run) and Calibri Light (2048, pt-BR run): bold advance = regular x 0.983, then 1/8 pt.
   Gulim 16 pt 15.75, 20 pt 19.625, 28 pt 27.5 (all on the eighth grid; the factor must lie in 0.9805-0.9834). Already landed (5919aec0d).

## Open: which property picks Rule A or Rule B

In the existing labs the face and the run language change together (Japanese faces only in ja-JP runs, Gulim only in ko-KR, Calibri Light
only in pt-BR). The font headers do not separate them: upem, head flags, OS/2 weight and fsSelection, embedded bitmap strikes were compared on
all five embedded subsets, and none splits {MS Gothic, MS PGothic, HG} from {Gulim, Calibri Light}.
Lab sbold decides it in one round: MS Gothic, MS PGothic, HG Maru Gothic M-PRO, Gulim, Calibri Light, Malgun Gothic (real bold, control)
x ja-JP / ko-KR / en-US runs x kanji / Latin text (nnnnnnnnMMMMMMMMiiiiiiii) x regular / bold x 24 and 18 pt, no wrap, no autofit, zero insets.
Read it with tab.py. At 24 pt a kanji is 24.125 under Rule A and 23.625 under Rule B. The Latin rows also show whether Rule B is
proportional (n, M and i narrow by different amounts) and whether Rule A adds one unit to Latin letters too.
Decision table: if the face decides, the rule follows the face in every language; if the run language decides, Rule A follows ja-JP.

## Our engine now (main 41414f618)

- SlideFonts.face(): every East Asian face with no bold cut gets bold = regular x 0.983 for its table glyphs (kana, Latin, punctuation);
  the em ideographs stay at 1.0 em in bold. Against PowerPoint for the Japanese faces that is 1.7% too narrow for kana and Latin and
  one unit too narrow for kanji (one eighth at 16 pt and up in MS Gothic and MS PGothic).

## Implementation (after sbold)

1. For a Rule A face: bold advance of every glyph, the em ideographs included, = (snapped design units + 1) / unitsPerEm em,
   then the 1/8 pt rounding as for regular. upem comes from the tsv header (puzzle 4). Keep the order: snap to units, add 1, scale, round.
2. Rule B stays as landed (x 0.983, then 1/8 pt).
3. Choose A or B by the property sbold names, never by a face list.
