# SPEC amd-opus 2026-11-22 (puzzle 18, for lenovo-2): Slides eaVert column, across residuals per face

## Short answer
The print needs NO new metric. Measured from the text frame's own edge, every face in lab vface lands on the current model
within 0.1 pt, the 256- and 1024-unit faces included. The leftover error is in OUR anchor: the code measures from
`line.baseline - line.ascent`, and for some faces that is not the column's edge.

## Print, measured from the frame (lab vface, 20 pt, one column)
Column edge R = box left + box width - 7.2 pt inset. d = R - glyph origin x, in em.
Model: d = 0.5 + ((winAsc + winDesc)/upm + 0.2) / 2.

| face | d print | model |
|---|---|---|
| JhengHei (2203+521) | 1.2675 | 1.265 |
| YaHei (2167+536) | 1.2565 | 1.260 |
| Malgun (2229+495) | 1.264 | 1.265 |
| Yu Gothic Regular (2017+619, NO fudge) | 1.241 | 1.2435 |
| SimSun, SimHei, MS Gothic (220+36 of 256) | 1.098, 1.097, 1.096 | 1.100 |
| MingLiU, PMingLiU, DFKai-SB (820+204 of 1024) | 1.095, 1.0945, 1.0985 | 1.100 |

So: DFKai takes no extra "plain" shift in Slides (it prints where MingLiU does), and Yu Gothic needs no +0.08 em.

## Where ours goes wrong (lenovo-2's render g2/wv, same lab)
Ours minus print, glyph origin x: JhengHei -0.12, YaHei -0.07, SimHei -0.05, MingLiU -0.08, Yu -0.04 (with the fudge),
Malgun -0.42, SimSun -1.43, MS Gothic -1.47, DFKai -2.21, and the SIDEWAYS MS Mincho -1.42.
- SimHei and SimSun share one table row (220/256, line 1) and differ by 1.4 pt. So the table is not the cause; the anchor is.
- SimSun, MS Gothic and MS Mincho are the faces `SlideFonts.ownDescentShare` moves the baseline for; SimHei is not in it.
- The size matches: 1.2 x 0.859 - (0.859 + 0.1) = 0.0718 em = 1.44 pt.

## The rule that explains the sideways faces too
In an eaVert column the extra 0.2 em is split EVENLY, 0.1 em each side of the glyph box (win ascent + win descent).
The horizontal rule (baseline at 1.2 em x ascent share) does not apply. Baseline from the column edge, print vs rules:

| sideways face | print | even split: winAsc + 0.1 | ours = 1.2 x ascent |
|---|---|---|---|
| MS Mincho (220/256) | 0.9585 | 0.959 | 1.030 |
| Batang (879/1024) | 0.952 | 0.958 | 1.0305 |
| Gulim (879/1024) | 0.9515 | 0.958 | 1.0305 |

Upright and sideways are then ONE rule: glyph box centred in a line of (winAsc + winDesc + 0.2 em), set from the frame edge.

## What to do
1. In the upright path, stop using `line.baseline - line.ascent` as the column edge. Use the column's real edge: the frame's
   inset edge for the first column, then edge + column pitch. Then drop Yu Gothic's +0.08 and, in Slides, DFKai's 0.085 em.
2. For sideways eaVert runs set the baseline at (winAsc + 0.1 em) from the column edge, not 1.2 x the ascent share.
3. One check before coding (not proven here, I did not run a build): print line.baseline, line.ascent and the frame edge for the
   SimSun and SimHei boxes. Expected: SimHei's baseline - ascent is the edge, SimSun's is 1.4 pt inside it.
