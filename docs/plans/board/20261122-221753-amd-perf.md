# amd-perf: local Common Crawl office-file search (starling2)

Where: `ssh starling@192.168.68.59`, folder `/data/ccindex` (README.md there). Run everything under `nice -n 19 ionice -c3`.

- Index: every pptx/ppt/docx/doc/xlsx/xls (and pptm, ppsx, ppsm, docm, xlsm) row of the Common Crawl columnar index, per crawl, in local Parquet. First 4 crawls (2026-43, 39, 34, 30) took about 4 h and are 38 MB; the 20 older main crawls back to 2024-46 are being added one at a time.
- `ccq`: query, TSV out. `--ext --tld --host --domain --host-like --url-like --url-re --crawl --full --limit --sample --by <col> --count --sql`.
- LANGUAGE: Common Crawl leaves `content_languages` EMPTY for every office file (it only detects it on HTML). So ingest also builds a host-language table (HTML pages per host and primary language, one Parquet per crawl in `hostlang/`). `ccq --host-lang zho` returns office files on hosts whose HTML pages are mostly Chinese (`--hl-share 0.5`, `--hl-pages 3`), any TLD. Real language of a file still needs the file's text.
- `ccfetch`: reads ccq TSV on stdin. WARC range first (payload cut to the WARC block length, then HTTP Content-Length or chunked, gzip decoded; `ccfetch --selftest` checks zip ends exactly at its end record), else the original URL (robots.txt honoured, 1 request per host per 5 s, 2 retries, honest User-Agent).
- Politeness / traps: data.commoncrawl.org answers 403 for a few minutes when hit with many small range requests (duckdb over httpfs). Ingest therefore downloads each index part whole (about 600 MB, one request), one at a time, and deletes it after reading. 403 is handled by probing until open again. A stale second ingest process doubled the load once: kill by PID.
- First numbers (4 crawls, a file crawled twice counts twice): pptx+ppt on zho hosts 245, jpn 484, kor 166; xlsx+xls zho 10014, jpn 12945, kor 1991.
