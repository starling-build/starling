# SPEC (amd-opus, 2026-11-22): a reader for legacy Excel .xls (BIFF8)

Design only, no code. Asked by starling-bd. Whoever builds it should CLAIM this entry.

## What the 100 books actually hold (measured, not assumed)

I walked every record of the 100 `.xls` books in `/data/corpus-cache/test/corpus/xlsx2/books/`
(script: `/data/s/amd-opus/scratch/xlshist.py`, a 60-line container + record counter).

- All 100 are OLE compound files. 99 are BIFF8. 1 is BIFF5 (Excel 95: stream named `Book`).
- 3 books name the stream `WorkBook`, not `Workbook`. Stream names must be matched case-insensitively.
- None is encrypted (no FILEPASS record). None is over 5 MB.
- 338 sheets in all. Cells: 174,268 shared-string cells, 34,647 RK numbers, 28,675 plain numbers,
  9,193 multi-RK runs, 20,113 multi-blank runs, 26,775 blanks, 7,187 old inline labels (2 books).
- Formulas are rare: 12,850 formula cells in 24 books (13 books use shared formulas). 76 books have none.
- Merges: 71 books. Custom number formats: 86. Palette: 28. Excel 2007+ colour extensions (XFEXT/THEME): 56.
- Page setup records are in nearly all (SETUP 97, margins 85, header/footer 96, manual page breaks 13).
- Defined names: 44 books (this is where print areas and print titles live).
- Drawings: 31 books (22 with objects). Charts: 4 books. Hyperlinks: 13. Conditional formats: 5.
  Data validation: 5. Notes: 2. VBA: 7. Freeze panes: 16.
- 98 of the 100 have an Excel print (`excel-20261122/xls-<id>.xls-orig.pdf`).
  No print: xls-2e6a44fb52, xls-dc3c7099da.

So: values + styles + page setup cover the print of about two thirds of the books outright;
drawings are the next biggest piece (31 books); formulas matter for 24 and only for editing,
because the cached values already print.

## The main design choice: translate to xlsx parts, do not fill the model by hand

Our Sheets model is xlsx-shaped. Page setup, margins, breaks, header/footer, print options are
kept as raw xlsx XML fragments (`Worksheet.keptElements`, read by `SheetPrintSetup`), column and
row attributes are kept as xlsx attribute dictionaries, and styles carry a `StyleSource` taken from
`styles.xml`. `Xlsx.read` (1,700 lines) holds every width, height, colour and style rule we have
tuned against Excel.

Proposal: `Xls.read(bytes)` = BIFF records → a small in-memory set of SpreadsheetML parts
(`[ZipEntry]`: workbook.xml, styles.xml, sharedStrings.xml, sheetN.xml, rels) → the existing
`Xlsx.read` core. No zip is written; `Xlsx.read(_ data:)` gets a sibling that takes the entries.

Why:
1. One place for layout rules. A width or style fix lands for both formats.
2. Save-as-xlsx works at once (the book already has a package). We never write .xls.
3. The test becomes exact (see Test): Excel can convert the same book to .xlsx, and the two must
   lay out the same through our code.
4. BIFF maps onto SpreadsheetML almost field for field (it is the same Excel model), so the
   translator is mostly mechanical: column width is already in 1/256 character, row height in
   1/20 pt, header/footer strings use the same & codes.

Cost: the cells are serialised and parsed once more. The largest book is under 5 MB, so this is
well under a second. If a profile later says otherwise, the hot path (cell records) can fill the
model directly without changing the rest.

Rejected: filling `Workbook` directly everywhere. It would need a second copy of the style
resolution and hand-built XML fragments for page setup anyway.

## Pieces

1. `CompoundFile.swift` (shared). Lift the private `CompoundFile` out of `OfficeCrypto.swift`
   (it already handles 512/4096 sectors, the DIFAT chain, the mini stream, loop guards). Add:
   case-insensitive names, the storage tree (path lookup like `ObjectPool/_123/Ole10Native`,
   needed for .ppt and embedded objects), and a `streams` listing. Keep `OfficeCrypto` on it.
2. `BiffReader`. Record = type (2 bytes), length (2 bytes), body of at most 8,224 bytes; a longer
   body goes on in CONTINUE records. The reader hands out a record with its segment boundaries,
   because strings need them (trap 1). Every read is bounds-checked and throws; a bad length must
   never index past the array (a Swift trap is a crash on a hostile file).
3. `Xls.swift` (globals + sheets → parts), `XlsStyles.swift` (fonts, XF, palette → styles.xml).
   Later: `XlsFormula.swift` (token decompiler), `OfficeArt.swift` (shared with .ppt).
4. One opener. `main.swift:428`, `ReadBench.swift:102` and `SheetsShell.swift:274` each test the
   extension for "xlsx" and fall back to CSV. Replace with one `Workbook.open(bytes, name)` that
   sniffs content: compound file with a Workbook/Book stream → Xls; compound file with
   EncryptedPackage → today's path; zip → Xlsx; else CSV. Sniff, do not trust the extension:
   ".xls" files on the web are often HTML or xlsx (none of our 100 is, but users' will be).
   `Zip.read` today turns any non-encrypted compound file into "not a zip"; the opener runs first.
5. Shared-code rules apply (web build): byte arrays and our own helpers, no `String(format:)`,
   no `FileHandle.standardError`, `containsSubstring` not `.contains("…")`.

## What to parse, in order

Workbook globals (first substream):
- BOF (version 0x0600, type globals), CODEPAGE, DATEMODE (1904 dates), COUNTRY.
- BOUNDSHEET: name, kind (worksheet / chart / macro), hidden or very hidden, and the byte offset
  of the sheet's own substream. Seek by that offset; do not assume the sheets follow in order.
- SST + CONTINUE: the shared strings, including rich-text runs (kept for milestone 5; plain text first).
- FONT, FORMAT, XF, PALETTE, STYLE; then XFEXT + THEME (true RGB and theme colours, 56 books).
- NAME + EXTERNSHEET + SUPBOOK: at first only the built-in print area and print titles (they are
  stored as formula tokens, so a tiny decoder for area references is needed already in milestone 3).

Per sheet:
- DIMENSIONS; ROW (height, hidden, custom-height flag, default style); COLINFO (width, hidden,
  style, outline level); DEFCOLWIDTH, STANDARDWIDTH, DEFAULTROWHEIGHT.
- Cells: LABELSST, RK, MULRK, NUMBER, BLANK, MULBLANK, BOOLERR, LABEL, RSTRING,
  FORMULA (+ STRING) as its cached value only.
- MERGEDCELLS. WINDOW2 (gridlines, zero display, right-to-left, frozen), PANE, SCL.
- Page setup: SETUP (paper, scale, fit to N by M pages, orientation, page order, first page number,
  header/footer distances), the four margins, HEADER, FOOTER, HCENTER, VCENTER, PRINTHEADERS,
  PRINTGRIDLINES, WSBOOL (the fit-to-page switch), horizontal and vertical page breaks.

Leave for later: charts and chart sheets, drawings and pictures, text boxes, notes, VBA (keep the
storage bytes untouched, never run or parse), pivot tables, embedded OLE objects, external-book
caches, BIFF5 and older, encrypted books, and writing .xls (never: save as .xlsx).

## Milestones

Each is one PR or a few, and each has its own check.

- M0 Container + records + opener. A `--xls-dump` flag prints streams and a record count.
  Check: all 100 open and list the right sheet names (338 sheets); the count matches my script's.
- M1 Values. SST, all cell records, cached formula values, number formats, 1904 flag, sheet
  names/order/hidden, row and column sizes, merges.
  Check: cell-by-cell equality with Excel's own conversion (see Test), 99 BIFF8 books.
- M2 Styles. Fonts, XF (alignment, wrap, indent, rotation, borders, fills), palette, then XFEXT/THEME.
- M3 Page setup + print area/titles. First full print sweep against the 98 Excel prints.
- M4 Formulas. Token (RPN) decompiler to formula text, shared and array formulas, names, 3-D
  references. 24 books. Until then a formula cell is a value: it prints right but does not recalculate.
  Check: decompiled text equals the `<f>` text in Excel's converted xlsx.
- M5 Rich text in cells, hyperlinks, freeze panes, outline, autofilter, conditional formats,
  validation, notes, protection flags.
- M6 Drawings (31 books): the OfficeArt record reader, pictures, shapes, text boxes; then charts
  (4 books + chart sheets), translated to the chart parts our chart code already reads.
- M7 Leftovers by count: BIFF5 (1 book; byte strings in the book's code page), encrypted books
  (the default-password RC4 kind first), SpreadsheetML-2003 and HTML files named .xls.

Rough size: M0 to M3 is about 2,000 to 2,500 lines of Swift and gives a real print of most books.
M4 is about 800. M6 is the largest single piece.

## Test

Two checks, and the first is the important one because it is exact.

1. Reader check (no rendering judgement). Have the Windows helper save each of the 100 `.xls` as
   `.xlsx` with Excel (SaveAs, format 51) into
   `/data/corpus-cache/test/corpus/xlsx2/xls-as-xlsx/`. Then for each book compare
   `OfficeApp --sheet-layout book.xls` with `OfficeApp --sheet-layout book.xlsx`.
   Same Excel model in, same code after the reader, so any difference is a reader bug, by
   definition. Target: identical dumps. This needs no scorer and no tolerance. A small new script
   (`test/xls-reader-diff.sh`) prints the first differing cell per book and a count.
   REQUEST to starling-bd: please queue that conversion on Windows.
2. Print check. `test/xlsx-app-render.sh` against `excel-20261122/`. It takes only `.xlsx` today
   and looks for `NAME-orig.pdf`; it must also take `.xls` (the prints are named
   `xls-<id>.xls-orig.pdf`). Report page-count matches and the mean score for the 98, next to the
   same numbers for the converted `.xlsx` twins. The twins' score is the ceiling: a gap between
   the two is the reader's; whatever is left is ordinary Sheets print work and goes on the
   normal Sheets queue, not on this task.
3. Robustness. A unit test that truncates each of 5 books at 200 random points and flips random
   bytes: the reader must throw or return a book, never crash or loop. Unit tests for RK decoding,
   a string split across CONTINUE, and FONT index 4.

## Traps to know before starting

1. A string split across CONTINUE: the next segment starts with a fresh one-byte flag, and the
   text may switch between 1 byte and 2 bytes per character mid-string. Rich-run and extension
   blocks can split too, with no flag byte. This is the classic .xls reader bug; 34 books have CONTINUE.
2. String header: character count, a flags byte (2-byte characters; has rich runs; has extension
   data), then the optional run count and extension size, then the characters.
3. RK numbers: bit 0 means divide by 100, bit 1 means a 30-bit signed integer; otherwise the
   30 bits are the top of a double.
4. FONT index 4 does not exist: fonts 0 to 3, then the fifth record is index 5.
5. XF: style XFs and cell XFs share one table. A cell XF has "attribute used" flags; where a flag
   is clear the value comes from its parent style XF. Colour indexes: 8 to 63 are the palette
   (default palette when there is no PALETTE record), 64 and 65 are system colours, 0x7FFF is
   automatic for fonts. XFEXT overrides with the real RGB or theme colour.
6. A FORMULA's cached value: if the last two of its 8 bytes are 0xFFFF, the first byte says
   string (the text follows in a STRING record, possibly after a SHRFMLA or ARRAY record),
   boolean, error or empty string; otherwise the 8 bytes are a double.
7. SETUP has a flag meaning "paper, scale and orientation were never set": then ignore those
   fields and use the defaults. Reading them anyway gives random paper sizes.
8. Rows without the custom-height flag are auto-fitted by Excel; pass that through so our
   existing auto-height rule runs, as for xlsx rows without `customHeight`.
9. DEFCOLWIDTH is in characters without padding; STANDARDWIDTH (20 books) overrides it and is
   in 1/256 character.
10. 6 books have records of type 0 near the end (1,487 of them). Probably padding after the last
    EOF; confirm on one book in M0 and stop at it.
11. Limits are 65,536 rows by 256 columns; MULRK and MULBLANK carry their last column at the END
    of the record.

## Should a .ppt reader follow the same container code?

Yes for the container, no for most of the rest, and not yet.

- Shared: `CompoundFile` as is, and the OfficeArt (drawing) record reader built in M6. An .xls
  drawing and every shape on a .ppt slide are the same record family, so M6 is half of a .ppt
  reader's groundwork. Build `OfficeArt.swift` with .ppt in mind (no Sheets types in it).
- Not shared: the .ppt stream is not BIFF. It has 8-byte record headers, nested containers, and
  the live slides are found through the `Current User` stream and a directory of edits (a file
  saved several times holds old versions; the latest wins). Text, its styling and master
  inheritance are separate record sets. Pictures sit in their own `Pictures` stream.
- Size: I would put a .ppt reader at two to three times the .xls one.
- Order: after .xls M6. PowerPoint's conversion already covers the 114 decks, so nothing is
  blocked; the .xls books cannot open at all today. When it is built, use the same approach:
  .ppt records → PresentationML parts in memory → the existing Pptx reader, and the same exact
  test (our layout of the .ppt against our layout of PowerPoint's own .pptx conversion, which we
  already have for all 114).
- The same container also opens legacy .doc, if that is ever wanted.
