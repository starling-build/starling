## 1. ko-20984ba0fc row heights (17.3 against 14.5)

Measured again from amd-1's prints (lab/korow in /data/s/amd-1/starling, and the corpus print):

- Sheet1: rows 1-61 print 17.3, rows 62 on print 14.5. NOT 92/93 (column A holds row-7; the one 16.0 pt
  baseline step is A=54 to A=55, rows 61 to 62). Same in the original, A-trim, B-noht and C-swap.
- Sheet2 with ht removed (S-sheet2only-noht): rows 1-58 print 17.3, rows 59 on print 14.5. It is not "all 17.3".
- Saved top-left cells: Sheet1 R16, Sheet2 J13. 61 = 16 + 45 and 58 = 13 + 45. So the tall block is
  row 1 to (top-left row + 45) on both sheets: 46 rows from the saved top row.
- Inside the tall block, Sheet2 rows 30-32 print 16.8, lower than their neighbours. They are the rows holding a
  cell in the real Malgun face (font 5, no scheme). They also print 16.8 in the with-ht print. So rows with a
  non-Normal font are fitted to content everywhere; only rows holding nothing but the Normal font differ.
- Sheet2 with ht="17.5" (not custom) on rows 1-3: every plain row 14.5, no tall block.
- The print draws font 0 (Malgun, scheme=minor) in Calibri: the scheme wins, so Normal on the print box is
  Calibri 11 and its own default row is 14.5. 17.3 is the file's defaultRowHeight 17 on the pixel grid (23 px = 17.25 pt).

Reading (my inference, not proven): a row holding only Normal-font cells takes "the sheet default height", and
that default has two values in one print. Rows Excel lays out when it opens the sheet (row 1 down to the bottom
of the window, 46 rows from the saved top row) take the file's 17. The rest take the default Excel works out
itself from the Normal font (14.5). A stored non-custom ht that differs from the default makes Excel refit the
whole sheet, so the file's 17 is never used.

Proposed rule, by property. It applies only when sheetFormatPr has no customHeight and the file's
defaultRowHeight differs from the default we compute for the resolved Normal font:
1. Rows with any cell in a non-Normal font: content fit, as now.
2. If any row carries ht without customHeight: plain rows take the computed default (14.5 here).
3. Otherwise plain rows 1..(topLeftCell row + 45) take the file's defaultRowHeight on the pixel grid;
   later rows take the computed default.

Not known: whether 46 comes from the file (windowHeight 12350 twips) or from the print box's Excel window.
If it is the print box's window, it is a constant of our reference prints and not of the file: starling-bd decides
whether to model it.

One lab round settles it (base: Sheet2 alone with ht removed, 190 rows):
- L1 topLeftCell A1: expect tall rows 1-46.
- L2 topLeftCell J100: expect 1-145.
- L3 windowHeight halved (6175), top row 13: 46 rows still means the print box's window; about 23 means the file.
- L4 ht="17.5" (not custom) on row 150 only: expect all 14.5 (tests rule 2 away from the top rows).
- L5 defaultRowHeight="15": expect no tall block (file default equals computed).
- L6 no topLeftCell at all: expect 1-46.

## 2. chart-tdf133190 pie label wrap (label a at width 10)

Widths from the prints, 9 pt Calibri. Line boxes include a 2.0 pt trailing space; ink widths below.
"Datapoint with" 54.7, "Datapoint with word" 75.8, "word wrap 2, 1.5" 61.9, label a whole 118.8,
"wrap with more words" 83.0, "Datapoint with a very long" 96.6, "... long word" 117.6.

Findings:
- w10-a-p160 (57 / 51 / "1.5") is a different case. The label sits inside the pie there, so it is the
  inside-fit ladder (narrower wraps tried until one fits the slice), not the outside wrap.
- A fixed greedy limit fails at width 14 too. Label a (118.8) stays on one line, but label c breaks before
  "word" although "Datapoint with a very long word" (117.6) is narrower than label a.
- Smallest width that keeps the line count also fails: d at w10 would be 55 / 79 / 64; Excel prints 76 / 83 / 39.

Candidate rule (fits all 11 prints, one constant):
1. Wrap greedy at the limit L (0.2 x chart width - 7.7, as now). n = number of lines.
2. If n > 1, wrap greedy again at W = min(L, r x whole one-line ink width / n).
3. If the second wrap still has n lines, use it. Otherwise keep the first.
The prints bound r to 1.233-1.276; 1.25 is the natural value.

Checks at r = 1.25:
- a w10: n=2, W=74.3: "Datapoint with" / "word wrap 2, 1.5". Matches.
- c w14: n=2, W=112.7: "Datapoint with a very long" / "word wrap label 2, 1.5". Matches.
- d w10: n=3, W=84 (capped): same as greedy. Matches.
- d w14: n=2, W=122 (capped): same as greedy. Matches.
- c w10: n=3, W=75.2: 61 / 55 / 61. Matches, but "very long word wrap" is 75.2, within 0.1 pt of W: do not lean on it.
- w6, all three: W capped at L, same as greedy. Matches.

Confidence: medium. One constant against four binding cases, in a 4% window. An additive form
(W = average + about 16 pt) also fits, in a much narrower window. Confirm before landing with one lab round:
two-line and three-line labels at width 10 built so the break moves between r = 1.15, 1.25 and 1.35, and two
labels of equal average but different length to split ratio from additive.
