# DESIGN (for planner review): faster cell storage and calc order, fr-ed293d08c8 (amd-perf, 2026-11-23)

Status: design only, nothing built. fr-ed293d08c8 now 92 s (was 3m10) for 20 pages; 182k formulas, 215k VLOOKUP, 199k IF.

## Today
- Storage: one `[CellAddress: Cell]` dictionary per sheet. `Cell` is a fat struct (input String, parsed formula, value, style, cached value, arrayRef, rawFormula, keptAttrs dict, spillRange): ~150+ bytes, many refcounted fields. Every read copies it.
- Calc order: lazy. `value(sheet, addr)` evaluates a formula when first read, with visiting/done sets for cycles. No precomputed order; no graph on a first load (graph is built only for edits).
- Range reads: `rangeValues` per pass cache; key index for SUMIFS/COUNTIFS/VLOOKUP exact (landed).

## Profile (fr, 92 s, perf, user-space)
1. XML parse + building Cell structs + shared-formula expansion: ~19%.
2. Cell struct copies / dictionary lookups in value() and rangeValues: ~20% (retain/release of the Strings and dicts in Cell).
3. Formula evaluation (IF/VLOOKUP/arith, EvalValue boxing): ~35%.
4. Print/layout of 20 pages: ~15% (already cut by the reach memo).
5. Rest: hashing, string folding.

## Proposed changes, in order of risk (each its own PR, each checked for identical PDF text on the 20 pages and unit tests):
A. Split the cold fields out of Cell: keep `value`, `formula`, `style` hot; move input/cached/rawFormula/arrayRef/keptAttrs/spillRange into one optional `Extra` class reference. Cell shrinks to about 40 bytes and one retain. Expected: most of part 2 (maybe 10-15% of total). Touches every site that builds a Cell (mechanical, compiler-guided).
B. Lazy `input`: for a formula cell derive the text from the parsed formula only when asked (formula bar, save). Saves the String per formula cell at load (part 1, a few %).
C. Dense row storage for loaded sheets: rows as arrays of column slots instead of a dictionary keyed by address. Faster lookups, no hashing. Bigger change (every `cells[a]` site, spill, restructure); do only if A+B leave dictionary hashing above ~10%.
D. Calc order: not a topological sort. Lazy evaluation already visits each formula once; sorting would not cut work, and risks cycle semantics. Instead: avoid re-entry cost (`_visitingSet` insert/remove per formula) by a flat state byte per cell once C exists.

## Risks
Spill/array/restructure code reads Cell fields directly; the oracle tests hold Excel output, so they guard A and B. No behaviour change intended; any PDF text difference blocks the PR.

## Ask
Planner: OK to start with A (then B), and park C and D unless the profile after A says otherwise?
