## 1. amd-2, A4 page 2 "one dot over" (ar-82457ecd08, ar-91bf9b6e16): SOLVED, the bug is ours

There is no excess in Excel. Two things made it look like one.

1. The 4054 is a reading error. Excel's PDF positions drift: every 9 to 10 rows one pitch reads 121.25 instead of 121 (four times on this page). The lab print mg2-A shows the same drift on plain 121-dot rows (32 pitches span 3872.7, not 3872). Pagination is in whole dots: 28 rows x 121 + 5 rows x 133 = 4053. Room = 4961 - 450 - 450 - 8 = 4053. It fits exactly, with the 8-dot foot. Foot 8 stands, no exception.
2. Ours drops the row because our A4 is 595.28 pt tall = 4960.67 dots, a third of a dot short of the printer's 4961. Room comes out 486.32 pt, the rows need 486.36, and the 0.01 pt slack in `bands` does not cover 0.04.

Rule (by property): a paper's printable size is whole printer dots, round(mm x 600 / 25.4). A4 = 4961 x 7016, A3 = 7016 x 9921, A5 = 3496 x 4961. Letter and the inch papers are already whole. Use that size for the room (height and width) in SheetPrint.pages; better still do the fit test in whole dots (page dots - margin dots - 8, rows as whole dots).
Not proven: how Excel rounds a margin that is not whole dots (all labs used whole-dot margins). Keep the current conversion.
Check before landing: footbr and mrgn2 r2 should now break between k=8 and k=9 in ours too (before the fix ours would break one step early on A4).
Trap for word-rules-traps: do not read a page's row total off the PDF rules; count rows x whole-dot heights. Excel's PDF y drifts about +0.25 dot per 1000 dots.

## 3. amd-2 + amd-3, row line formula: two different quantities were in one table

P = the drawn pitch between wrapped lines in a cell. R = the row height per line. They are not the same number, and the joint table mixes them.

P, from the printer's GDI metrics at 600 dpi (h = tmHeight, el = tmExternalLeading), round half up:

    P = h + el + max(8 dots, el / 2)

22 measured cells, 21 fit exactly: PMingLiU 9-16 pt (98 109 119 130 152 172), SimSun (94 103 113 122 141 162), JhengHei (103 113 124 133 155 175, simply h + 8), Calibri 11 (121), Arial 12 (123, zwsp1 p3-4 and the ar-d7 book), Tahoma 12 (129). The 8 dots is most likely 1 pt (0.96 pt at 600 dpi); one dpi cannot tell.
Does not fit: Nirmala UI 12, in-cell pitch 148.4 (zwsp2 p3, Kannada and Latin alike) where the rule says 141. Malgun's 149 looks like the same thing (same GDI height 133): both h + 16. One size each, so no rule yet.

R, from the screen: a row of n lines is n x R, and R = the screen line in pixels x 6.35 dots per 96-dpi pixel (3.175 per 192-dpi pixel; the same factor that prints a 15 pt, 20 px row as 127 dots). Calibri 11: 38 px, 121. Arial 12 and Tahoma 12: 40 px, 127 (rows 127, 254, 382, 509, 636 in zwsp1). Nirmala UI 12: 50 px, 159 (159, 318, 477). So "Nirmala line 159" in the table is R, and its drawn pitch is 148. The lines are drawn at P inside a row of n x R (Tahoma: P 129 in R 127).
Open on R: in ar-d7e763fe3f the Arial 12 rows are 14.85 pt a line = 39 px, not 40 (sheet default 15.95, Normal font Calibri 12; the lab has Calibri 11). Not explained.
The table's MS Gothic 110, Yu Gothic 164, Meiryo 164, Malgun 149, Calibri 130 are "our table's rows": I could not tell which are P and which are R. Re-read them from their prints as P (baseline gaps inside one cell) and R (rule to rule, divided by lines) before fitting anything.

## 5. amd-1, pie ladder counterexample (chart-tdf136105): the ladder is for bestFit labels only

The property is the label position. pie4 (all books) and chart-tdf133190 have `c:dLblPos val="bestFit"`. chart-tdf136105 has `dLblPos val="outEnd"` on every label. Its labels print greedy at the wide limit ("Data Label 3 with long" 83.0 / "name 3; 1"), which is exactly greedy at L = 0.2 x 547 - pad (about 102 to 104): "... long name" would be about 109.
This is the same thing amd-6 saw in PowerPoint: the narrower forms are tried to make the label fit INSIDE its slice (bestFit). A label told to sit outside is never re-wrapped narrower.
Rule: ladder only when the label's position is bestFit (stated, or the pie default when dLblPos is absent). outEnd, inEnd, ctr: greedy at L, no ladder.
Proven by one book for outEnd; inEnd and ctr are my reading. Cheap confirmation if wanted: pie4's b6 and b7 with dLblPos outEnd, inEnd, ctr (6 books): expect 60 / 31-style greedy wraps, not 40 / 51.
With this, tdf136105 should stay at 92.9 and pie4 keeps its fits. tdf133190 not moving (57.1) is a separate miss.
