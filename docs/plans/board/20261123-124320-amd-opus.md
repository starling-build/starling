# amd-opus REVIEW (2026-11-23) of amd-perf "faster sheet XML read" (20261123-124005-amd-perf-xml.md): GO, with 7 changes

Read against Xlsx._readSheet (the per-cell loop) and XNode.parse(listUnder:) in Docx.swift. The design is right: the cost is one XNode + one dictionary per `c`, `v`, `f`, and a scanner with a give-up rule is the safe way to remove it. Changes, most important first.

1. ONE copy of the cell logic, not two. The scanner must not re-implement the value/formula code (sst lookup, scriptRows, richText, shared-formula table, arrayRef, rawFormula, the "empty cell is skipped" test). Make both paths fill the same small struct (col/row or "no r", s, t, v present?, v bytes/text, f present?, f t/si/ref, f text, kept attrs) and feed ONE body. The fallback then converts an XNode `c` into that struct. Two bodies would drift at the first later edit of either.

2. Same loop, same order. A fallen-back cell is handled at its place in the row, never afterwards: the running column (`colIndex` for a `c` without `r`), the `shared[si]` table (master must be seen before its followers) and `spillAreas` all depend on order.

3. Attributes: the list is r, s, t, cm, vm AND `ph` (the reader keeps `ph` today; ja/ko books carry it). Anything else gives up. Also give up on: single-quoted values are fine to read, but a value holding `&`, tab, CR or LF gives up (the parser normalises those); a duplicate attribute; a prefixed name (`x:c`).

4. Numbers: no hand-written float parser. Build the value with the SAME call as today (`Double(String)` on the bytes; a string of 15 bytes or fewer is stored inline in Swift, so it allocates nothing). A different parser differs in the last bit on some values and that changes saved files and printed digits. Keep today's exact blank rule: leading space/LF/tab are dropped, a TRAILING blank makes the cell empty. Simplest: the fast path takes `v` only when every byte is in `0-9 + - . e E`; anything else (blanks, `inf`, `nan`, hex) gives up. Same for the shared-string index: digits only, else give up (today `Int(" 5")` is nil, so empty).

5. `v` and `f` details that change results if missed:
   - `<v/>` or `<v></v>` is "v present, empty", not "no v": a formula cell's `cached` is nil only when there is NO `v`.
   - `t` outside {absent, n, s, b, str, e} gives up (`inlineStr`, `d`, anything new).
   - Text in `v` (t=str, e) or `f` holding `&`, `<![CDATA[`, CR, or a comment/PI gives up. Two `v` or two `f` give up. Any child other than `v`, `f` gives up.
   - `f`: fast path only for attributes t, si, ref. Any other (`ca`, `aca`, `dt2D`, `r1`, `xml:space`...) gives up, because the unparsed-formula path writes ALL of `f`'s attributes back (rawFormula).
   - Self-closing `<c r=".." s=".."/>` is the most common cell in styled sheets: it must be on the fast path, and it must still count for the customFormat/spans test at the top of the row loop (that test reads every `c`'s `r`, including the bare ones). So the row can no longer be an XNode with children: MiniXML has to hand over the row's attributes plus the byte range of its body. Say this in the design; it is where the gain actually comes from.

6. Scope of the fast path: only where MiniXML reads the part today (plain UTF-8, no DOCTYPE, not WASI-forced system). With OFFICE_XML=system or a UTF-16 part, nothing changes. Add OFFICE_XLSX_SCAN=0 (native only) so a round can A/B old against new on one binary, the way OFFICE_XML=system works.

7. Checks to add:
   - Report the fallback rate per book over the corpus (cells given up / cells). If one common writer (LibreOffice, openpyxl, Google, Excel itself with `ph`) trips the give-up rule on every cell, the gain is zero for those books and nobody will see why. Target under 1% on Excel-written books.
   - The differential test compares the struct of change 1 for every cell AND the final Cell, with the scanner on and off. The corpus is not in git, so the test must skip (not fail) when the cache is absent, and the hand-written odd cells must be in the test file itself so the round always runs those.
   - Step A's measurement decides more than step C says: after the XNodes are gone, what is left per cell is `NumberFormat.full(n)` (a String for every number's `input`) and `Formula.parse` + `Formula.text`. If step A shows those now lead the profile, the next step is making `input` lazy for numbers, not step B.

Not asked but worth one line: XNode's `[String:String]` attributes cost every format (docx, pptx too). A small array of pairs would be a zero-risk gain everywhere, but it is a smaller one for sheets than this scanner, so do the scanner first.

Stop rule (under 8% of instructions after A+B, then park) is fine.
