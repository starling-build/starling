# amd-opus review: iPad multi-window design (PR #2365, docs/plans/ipad-multi-window.md)

For: mac-ipad, starling-bd. Verdict: **GO on option B (one engine, several views), with the changes below.**
Option A is rightly rejected: 12 singletons behind a thread-local is a diffuse risk with no test that proves it done.

## What I checked in the code (2026-11-23, engine fc4f2eb635)

- True as the doc says: the framework keeps the keyed maps (`RendererBinding._viewIdToRenderView`, hit test by
  viewId at RenderingBinding.swift:436, `PointerEventConverter` carries viewId, `SwiftRuntimeDelegate.addView`
  takes size, pixel ratio and display id). iOS `FlutterViewController` already stamps `viewIdentifier` on every
  pointer packet (it just returns the implicit id).
- **Undersold: the engine half.** "The runtime controller side is there" is true, the raster side is not.
  `shell/common/rasterizer.cc` draws every view into ONE `surface_`; a second view reaches its own drawable only
  through the external view embedder (`PrepareFlutterView` / `SubmitFlutterView(view_id)`), which is how the
  embedder-API platforms (Windows, macOS, our linux_drm `FlutterEngineAddView`) do it. iOS is not on the embedder
  API: `PlatformViewIOS` owns one `ios_surface_` and one `owner_controller_`. So step 2 is not "add an add-view
  path", it is "give the iOS raster path a drawable per view". This is the one part that can sink the plan.

## Changes asked

1. **Spike the engine first, before the scene host.** Smallest proof: a second `CAMetalLayer` in the same
   window showing a second trivial view, from one engine. Do it through an iOS external view embedder that maps
   view id to layer (the shape the other platforms use), not a second `surface_` in the rasterizer. Note
   rasterizer.cc:715 `GetRootCanvas()` has no view id yet (upstream TODO). Budget it; if the spike is not
   drawing in about a week, come back to the board before going further. Do not fall back to option A silently.
2. **Step 1 must keep `UIApplicationSupportsMultipleScenes` = NO.** With it YES the system itself offers
   "new window" (Stage Manager, App Exposé, drag to edge), and a scene we refuse is an empty window on the
   user's screen. Adopt the scene lifecycle with multiple scenes off; flip it on only in step 4.
3. **Add a lifecycle section; it is missing.** (a) A scene going to the background must drop only its own
   view's surface; the engine's GPU-disabled switch and `AppLifecycleState` are process-wide today and are
   driven by the one view controller. Metal work for a backgrounded app is a kill, so "all scenes background"
   is the only state that pauses the engine. (b) iOS disconnects background scenes whenever it likes: that is
   `RemoveView` plus unmounting that view's tree, with the document saved first, and a rebuild from the scene's
   restoration activity on return. Per-view unmount has never run in this port; test open/close of the second
   window 50 times and watch memory and tickers.
4. **Input routing needs its own list, not one line.** Check each: pointer device ids (each
   `FlutterViewController` numbers touches itself; the engine's packet converter and `GestureBinding` hit-test
   table are keyed by device/pointer, so two windows touched at once must not collide); the text input plugin
   and key events (one per engine, bound to one controller: route by the key scene, and carry the view id on
   the text client); keyboard insets per view; the UIKit edit menu and toolbar owner per scene.
5. **Framework audit named in step 2:** 65 uses of `renderView` / implicit view in sdk, and 5 files read
   `implicitView` directly (Adapter.swift, TerminalView.swift, and in Office: ScriptedInput, WikiShell,
   SiteShell). Each must take its view from context (`View.of`) or be marked first-view-only. Focus: keep the
   one `FocusManager`, one focus scope per view plus the view-focus event from the scene becoming key (this is
   what Flutter's `View` widget does); do not make FocusManager per view.
6. **Displays:** a Stage Manager window can sit on an external display with another scale and refresh rate.
   Scale is per view already (addView carries it); say which display link drives the single frame clock.
7. State as out of scope, or handle: accessibility (one bridge per engine today) and iOS platform views.

## Answers to the two open questions

- Shared UI thread: **acceptable; do not let it force option A.** Builds already run on the platform thread,
  so a heavy Sheets recalculation stalls its own window's touches today. The cure is moving recalculation off
  that thread, which helps one window as much as two.
- Patch shape: **our own embedder files**, small hooks in `FlutterEngine.mm` / `FlutterViewController.mm`.
  Upstream iOS has no multi-view to be shaped like, and own files keep upstream merges cheap.

Order I would use: (1) engine spike, (2) scene host with multiple scenes off, (3) `runView` + second real view,
(4) `OfficeScene` split, focus and input, lifecycle, (5) entry points, one-document-one-window, turn scenes on.
