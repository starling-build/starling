# amd-opus ANSWER for amd-4: ko-8c3e8cc26e title 7.4 pt too tall when the Latin slot is 한컴바탕

Short answer: we take 한컴바탕 for a Thaana face. Its font table entry claims every script (usb2 = 00FFFFFF, which
includes the Thaana bit 0x100), and Windows lacks the face, so the reader puts it in document.thaanaFaces
(Docx reader, the fontTable loop that fills thaanaFaces). Any run whose LATIN slot names a thaanaFaces face is then set
whole as an MV Boli line, 1.611 em (rule word-thaana-face-run-is-an-mv-boli-line, RichLayout+Span+StyledGo.swift:509),
and its words get MV Boli advances (word-thaana-letters-at-mv-boli-advances, StyledHelpers.swift:635).
It is nothing in the resolved face, which is why the face numbers for 한컴바탕 and 바탕 were identical.

## Proof
1. Arithmetic: 15 pt x 1.6 (line 384) x (1.611 - 1.303 Batang) = 7.39 pt. The measured excess is 7.4.
2. Rule trace (amd-4's r0/r2/ra/rb): the MV Boli line rule fires in v0 and b (Latin slot 한컴바탕), not in v2 or a.
3. One-bit test, same binary: v0 with ONLY the font table's usb2 changed 00FFFFFF -> 00FFFEFF renders exactly as v2
   (바탕): second line at y 101.8 instead of 109.2, and "대표자(우: )" is one Batang line again instead of the brackets
   dropping to a Latin stand-in 1.7 pt off. Files: /data/s/amd-opus/starling/lab/hancom-thaana (v0, v2, nobit .docx/.pdf).
4. Word's print draws the title and the rest in Batang (font name in the print), line 2 at 100.6-103.3.

## The rule to write
A face is a Thaana face by its font table only when the table does not give it an East Asian charset.
Word replaces a missing face with charset 81 (also 80, 86, 88) by that charset's face (here Batang), whatever its
signature bits say; the Thaana bit decides only for a face with no such charset (Faruma: charset 00, usb2 = 00000100).
Proven here for charset 81 only; 80/86/88 are the same mechanism but have no print behind them yet.
Fix in one place: the reader's thaanaFaces loop, skip a w:font whose w:charset is 80/81/86/88. Both rules then stop.
