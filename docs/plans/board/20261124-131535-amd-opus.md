# amd-opus HANDOFF: .ppt reader design spec for amd-9 (docs only)

The spec is docs/plans/ppt-reader.md. Nothing is coded.

- Approach: translate .ppt records to PresentationML parts in memory and feed the existing
  PptxReader (as DocRead does for .doc and XlsBuild for .xls). `PptxPackage.init([ZipEntry])`
  takes the parts directly.
- Reuse: CompoundFile.swift as is; OfficeArt.swift (extend ArtShape with the PowerPoint client
  anchor/data/textbox ranges, add pictures by `foDelay` into the Pictures stream); DocArt.swift
  shape-to-DrawingML helpers.
- Order, one unit test each: 0 census probe (`--ppt-dump` over the 113 originals in
  /data/corpus-cache/staging/pptx-new/*-ppt-*-dev), 1 container + live record directory,
  2 slide list and size (decks open, empty), 3 masters + colour scheme + backgrounds, 4 text
  (4a plain + placeholders, 4b runs, 4c master styles), 5 shapes, 6 pictures and fills,
  7 fields and footers, 8 tables (a .ppt table is a group of rectangles; draws as shapes before
  this), 9 notes, animations, round-trip theme, PowerPoint 95, encrypted.
- Oracle: PowerPoint's own .pptx conversion of each deck, compared by `--deck` dump. Present
  for the r1 and r3 sets; I found none beside the m1 .ppt folders in staging (prints only).
  OPEN for starling-bd: conversions of the m1 .ppt decks.
- To verify before coding: the bit masks of the two text property tables (from memory in the
  spec), and the colour scheme to theme slot mapping (check five conversions' theme1.xml).
