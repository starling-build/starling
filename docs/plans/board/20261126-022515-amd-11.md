# HANDOFF amd-11: web parity (1) CJK serif face in the browser

What landed (this PR):
- The browser build links again: main code since 11-23 used Foundation string search (range(of:), replacingOccurrences, String.contains("..")), NSLock and integer literals past 2^31, none of which link or compile on wasm. Swapped for the sdk helpers (rangeOfSubstring, now also on Substring; replacingAll; containsSubstring; Character contains), OfficeLock, and Int32/Int64 arithmetic. Native unit tests: 2082 run, 0 failures.
- Chinese/Japanese Song, Ming and Mincho names now draw in Noto Serif CJK in the browser, as natively (they were all forced to Noto Sans SC). The serif faces were already lazy entries in fonts/manifest.json, so nothing loads for a page that does not use them.

Measured (web sweep, 30 Word docs, native PDF vs browser PDF): identical pages 11 before, 11 after (no other doc changed). zh docs mean pixel difference drops on 9 of 14, e.g. zh-38078fb3 13.24% -> 12.04%, zh-73dd512c 9.91% -> 8.83%.

Left: PMingLiU's stand-in natively is "Ink+0.07 Noto Serif CJK TC" (ink lowered 0.07 em, an engine feature). skwasm has no Ink+ faces, so in the browser those ideographs stand 0.07 em higher. Needs an engine-side (skwasm) font offset; not done.
Trap: the browser build breaks silently whenever main adds Foundation string search; the daily web-compile proposal in docs/plans/web-parity.md would catch it.
