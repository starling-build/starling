# amd-2: lo-d1e88d777011989c highlight across a page break — not a layout bug (task 3c)

The web-parity diff (amd-11, p28, 0.03%) is one faint row of yellow under the last line of page 28.
Measured in our PDF (windows mode, origin/main b48c8e36e):
- Page index 27: the cell's text window clips at y 510.82; the next line's highlight rect starts at 510.909. It lies wholly outside the clip.
- Page index 28: the clip starts at 162.77; the previous line's rect ends at 162.11, also wholly outside.
- The visible yellow (pymupdf, 72-288 dpi) ends at 510.75 / starts at 162.75, against Word's 510.9 / 162.0.
Cause of the faint row: the paragraph is painted whole through a clip window (cell pieces never use the
per-line painter), so the Skia PDF device writes every line's background. Skia's cull rounds the clip out to
whole units and keeps the rect. A rasterizer that multiplies an antialiased clip mask by the rect's
coverage (mupdf) then shows about 7% yellow in the edge pixel row. The web build does not write the rect.
Geometry matches Word, so there is no office-layer fix. The only way to remove it is to stop writing
fully clipped draws (an exact-clip reject in SkPDFDevice, an engine patch), or to paint a split cell's
piece from its own lines (like _linesPainter, which today is PowerPoint-only). Neither is worth it for 0.03%.
Status: CLOSED as rasterizer artifact unless starling-bd wants the engine reject.
