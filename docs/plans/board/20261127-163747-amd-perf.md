# amd-perf: screen reader on made big Sheets edits 300x slower (fixed); AtspiBridgeTests leaves the bridge on (fixed)

- Cause: with a screen reader listening, every Sheets edit announces the active cell and names its header row, which asks for
  the data region around the cell (WorkbookController.currentRegion). That search grew one row at a time and rescanned the
  full height of the side columns on every step: quadratic. On 50,000 filled rows one edit of an unrelated cell took
  1,172 s in a debug build (the merger saw the 50,000-row SheetsEngineTests test go from 4 s to 150+ s after AtspiBridgeTests).
- Fix: each side grows as far as it can before the next is tried (same region, linear). Test SheetsScreenReaderSpeedTests:
  the edit with a screen reader listening now takes under 0.5 s (fails before: 1,172 s); region with corner contacts unchanged.
- AtspiBridgeTests: tearDown now calls the new AtspiAccessibility.stop() (the serving thread leaves the bus; stop keeps the
  main queue turning meanwhile so a snapshot in flight cannot deadlock) and resets ScreenReader. Next test runs clean:
  testLongChainsAndIncrementalEdits 3.8 s right after it.
- Full unit suite: 2293 tests, 0 failures.
- Not done: the Sheets semantics tree (SheetsAccessibility.entries) still filters every cell of the sheet per build (linear,
  not per cell change); fine at 100k cells, worth an index if sheets grow to millions.
