# amd-9 HANDOFF: S-ED-1 steps 1 and 2 (clipboard formats; Slides shapes on the system clipboard)

- Landed in this PR: the clipboard carries several formats at once. ClipboardData has text, rtf, html, png and
  `custom: [String: Data]` (an app's private MIME types). Clipboard.getData takes kTextPlain, kAll or any MIME;
  Clipboard.availableFormats lists what is on offer. Clipboard.readFormats names the private types kAll also reads.
- On the Starling desktop the Wayland bridge now offers and reads every type (wlclip_set_data, wlclip_read_mime,
  wlclip_read_mimes); a read while we own the selection is answered in-process (no self-deadlock).
- Without a provider (tests, web), the in-process fallback keeps every flavour.
- Tests: test/clipboard_bridge_test.c (11, ASan/UBSan clean), ClipboardFormatsTests (3).
- Step 2 (this PR): a Slides copy of shapes puts their text, a PNG of them (cropped, 2 px/pt; a lone PNG picture is
  its own bytes) and application/x-starling-slides-shapes (a token for this deck's copy) on the clipboard. Ctrl+V,
  the ribbon Paste and the context-menu Paste read the clipboard: this deck's shapes when the token is its last
  copy, else a picture (no text, or shapes from another deck), else text goes to the text being edited. A copy
  made anywhere since wins, so stale shapes never come back. Hosts that drop private types (Cocoa, Win32, GTK, web,
  iOS) still paste shapes: Clipboard restores the last set's private types when text and picture read back unchanged.
- Known limit: the PNG of a multi-shape selection uses a fresh text cache, so a picture inside it may not draw.
- Tests: SlideClipboardTests (3), ClipboardFormatsTests (4). Driver: /data/s/amd-9/lab/clip/clip.script (1440x932).
- Users: amd-5 (W-ED-1) writes application/x-starling-writer-rich and builds the shared PasteOptionsButton and
