A desktop where every app
is a widget

A desktop environment is normally four programs in three languages, talking over IPC. Starling is one GUI application. The dock, the menu bar and every window on screen — including Chrome and Zoom — are widgets in a single tree. That one decision is why the whole desktop fits in 60,000 lines.

Four minutes, one take — recorded by the desktop itself, with its own screen recorder. The App Store really downloads Chrome and VS Code and installs them with apt; both then launch from the desktop's own launcher.

The idea

One tree, all the way down

Build a desktop the usual way and you build four things. A compositor that owns the screen. A window manager that decides where things go. A panel and a launcher, usually in a different toolkit. And the toolkit your own apps are written in. Four programs, three languages, and a protocol between every pair — each boundary a place where an idea has to be re-implemented on both sides, or abandoned.

Starling deletes the boundaries. There is one GUI framework and one widget tree, and everything on screen lives in it. The dock is a widget. The menu bar is a widget. A workspace pane is a widget. And a Chrome window — a foreign program that has never heard of Starling — arrives as a dma-buf, becomes a texture, and is composited by a widget sitting in that same tree, next to the dock.

Window management becomes layout. Compositing becomes painting. Animation is just animation.

That is the whole thesis, and it is worth being concrete about what it buys. Tiling a window is not a window-manager feature, it is a Row. Moving a live app into a pane is moving a widget. Fading a window as it closes is the same code that fades anything else. Effects that need a compositor plugin elsewhere are ordinary framework animation here, because there is no elsewhere — no second process, no protocol, no other language.

The usual stack
  • Compositor, window manager, panel, toolkit — separate programs
  • Windows are protocol objects, owned by another process
  • New window behaviour means a compositor patch or an extension
  • Effects live in the compositor; your UI cannot reach them
Starling
  • One application, one language, one widget tree
  • Windows are widgets — a client's buffer is a texture in the tree
  • New window behaviour is a layout change
  • Effects are framework animation, on the same tree as the dock
What falls out of it

Features that would be projects

None of these are clever. They are what you get for free once a window is a widget — which is the point.

Workspace mode — 916 lines

A named workspace with an agent driving on the left and whatever it opened captured as tabs on the right. Live apps, resized into panes, switching with the workspace.

Elsewhere this is a window-manager feature: reparenting foreign clients, tracking them, re-laying them out. Here the pane is a widget and the app inside it is a widget, so the whole mode — rail, panes, tab strip, drag-and-drop — is one 916-line file.

Shell/WorkspaceSpace.swift

X11 and Wayland, in the same scene

Starling is a Wayland compositor and hosts its own X server. Zoom is an X11 client; Chrome is a Wayland one. They composite into one desktop, on one GPU path, with no session picker and no XWayland shim between them.

Both servers terminate in the same place — a texture. The shell has no X11 path and no Wayland path; it has a widget that draws a texture, and two servers that produce one. The Wayland compositor is 6,900 lines of C, the X server 5,700.

Sources/WaylandServer · Sources/X11Server

Glass that is actually computed

The dock doesn't fake depth with a blur. A fragment shader gives the panel real thickness, derives a surface normal from it, and bends the view ray through that normal with Snell's law — then adds a Fresnel rim and a specular highlight riding the same surface. Look at the text passing behind it: it doesn't just blur, it bends and compresses toward the rounded ends.

And there is no compositor extension to ask for it. The dock is a widget sitting above the window widgets in one tree, so it can simply read what is under it. Elsewhere that is a protocol negotiation between two processes; here it is a shader over a scene you already have.

Plus a 7,500-line DRM/KMS embedder in the engine fork: about 60,000 lines for the desktop, its two display servers and its apps. Counts exclude build output and the Wayland protocol code generated by wayland-scanner. What makes them possible is the part that is not small — a 211,000-line port of Flutter's framework to Swift, with no Dart VM under your session, which every app and the shell itself are written against. Desktop and engine are both public.

Why it matters

The cost of building a desktop just collapsed

Sixty thousand lines is the architecture's doing. That it exists at all — six months, one person directing, the code written by AI — is the other half, and the two multiply. A desktop this small is one a model can hold in its head, and a change lands in one language instead of being negotiated across four programs.

For three decades, building a Linux desktop has been the work of institutions. GNOME and KDE are extraordinary pieces of engineering, sustained by hundreds of contributors across decades. That isn't a criticism of them — it's a measure of what a desktop has cost to build.

And that cost is why there are so few. Why the ones we have are hard to change from outside. Why a genuinely new idea about how a desktop should work has had almost nowhere to go except a fork, an extension, or a patch queue someone else controls.

One person, six months, a complete desktop. Not by cutting scope — it drives the GPU, runs Chrome and Zoom, survives a monitor being unplugged.

That number is the whole argument. If a single person can now reach this point, then the constraint on Linux desktop development was never imagination and never taste. It was labour. And labour is exactly what just got cheap.

The interesting consequence isn't Starling. It's the ten desktops after it — attempted by people who never had a decade to give, who would have looked at the size of the job and picked a smaller one. That floor has moved, and the rate at which Linux desktops get built should move with it.

This is the time to build.
The desktop

Everything else a desktop has to do

Not a proof of concept with the interesting parts missing. Every screenshot below is the real thing, captured from a running session.

Tiling and floating, both first-class

Floating windows by default. Flip one switch and everything arranges itself master-and-stack, the way a tiling window manager does — whatever you are working in holds the master pane, everything else stacked beside it.

Flip it back and every window returns to exactly where it was floating. No extension, no separate desktop to switch to, nothing to relearn.

Settings → Appearance → Tiling Windows

Spaces and Mission Control

Slide between virtual desktops, carry a window along as you go, or pull back with one key and see every space at once. Anything you send fullscreen quietly becomes a space of its own.

Drag a window between spaces from the overview, or add a new one from the strip along the top.

Ctrl + ↑ for the overview · Ctrl + ← → to switch

Monitors that behave

Every display gets its own menu bar, its own wallpaper and its own spaces — but they are one desktop, not two. Park a window across the boundary and it just works: half drawn on one screen, half on the other, at each screen's own scale.

Unplug a monitor and its windows come home instead of vanishing off into nowhere. Plug it back in and the desktop picks up where it left off.

Hot-plug · per-display scale · per-display spaces

Nine apps, the same framework, no interpreter

Files, Terminal, Settings, Calculator, Text Editor, Image Viewer and an App Store that installs from the Ubuntu archive — each written in the same framework as the shell that hosts it. One theme change reaches all of them at once, because there is no toolkit boundary for it to stop at.

And all of it compiled ahead of time to machine code, binding only a stable C rendering core: no virtual machine under your session. Client buffers are shared straight off the GPU, never copied, and every app is its own process, so a crash takes one window and nothing else.

Install

One package, then pick Starling at login

Download Starling 0.2.3 (.deb, 51 MB) ↓ 
# Ubuntu 26.04 LTS, amd64. Starling needs a Wayland-capable login
# manager. Ubuntu Desktop already has one (GDM); on Server or a minimal
# install, add it first:
sudo apt install gdm3

# Download and install Starling with its runtime dependencies:
curl -fLO https://github.com/starling-build/starling/releases/download/v0.2.3-2/starling_0.2.3-2_amd64.deb
sudo apt install ./starling_0.2.3-2_amd64.deb

# Log out (or reboot). At the login screen click your name, open the
# session menu (the gear / lower-corner button), pick "Starling", sign in.
This is an early preview. Starling runs a real desktop on real hardware today, but it is version 0.2.3: expect rough edges, missing settings, and apps that still need work. Verified on AMD graphics under a fresh Ubuntu 26.04. The package pulls in a login manager if you don't already have one.

Testing in a VM? Use a virtual machine, not a container — Starling is the display server, so it needs a real GPU device and a logind seat, which LXC and Docker don't provide. VirtIO-GPU works.

Once it's running, the User Guide walks you through the desktop — the dock, spaces, shortcuts and apps.
