The workspace

Tiling or floating — one toggle.

The same workspace runs both ways. Tiling gives every shell a pane and draggable seams; floating gives each shell its own window and a cover-flow picker. Flip between them live, shells intact.

Performance

Measured against ghostty, on Linux and macOS.

Both platforms run ghostty's current nightly, configured onto our Roboto Mono at our cell metrics, at the same verified 47×201 grid — so cell for cell, both terminals raster the same pixels. Ten workloads, medians of three runs. Linux is a Ryzen 7 8845HS on GNOME/Wayland; macOS is a MacBook Pro (M1 Pro), our build on a full release engine. Every bar below is a multiple of ghostty's pace, on a log scale so a 2× win and a 2× loss have equal length: amber, rightward — Starling is ahead; grey, leftward — ghostty is. Every raw second sits in the tables at the end of the section.

The same suite repeated until each workload runs one to two minutes (~159 GB of escape-sequence traffic per terminal on Linux, ~30 GB on macOS), the cats grown to 500 MB, DOOM-Fire run to 150,000 frames three times over. Length is kind to both terminals, and on Linux it is kinder to us: the two workloads ghostty won at short range (light and dense cells, 0.85× and 0.69× above) converge to parity at steady state, and no Linux workload is behind by more than 2%. On macOS the fire converges to a tie at a shared ceiling; on Linux it widens to 1.94× — 1610 fps on ~1.8 cores against 830 on ~2.1. What never converges is cost: at steady state ghostty burns 1.9× our CPU on Linux and 3× on macOS for the same bytes. Every number is a pair measured back to back on one machine, and the raw runs are checked in at docs/perf (terminal-vs-ghostty-2026-08-13-atlas, terminal-vs-ghostty-macos-2026-08-13-samefont, and the two steady-state rounds, -long).

How it is built

From scratch, on a UI engine.

The emulator is about 1,500 lines of C we wrote — no libvte, no libvterm, nothing borrowed. The pixels come from the Flutter engine through the Starling SDK: a general-purpose UI engine, not a terminal-specific one.

That is the unusual part. Terminals this fast are normally built on a stack that can only ever draw a terminal. This one matches or beats them on their own benchmarks — and the engine underneath hands us the rest for free: the same code on every platform, and a real widget tree around the grid, which is where the splits, the floating frames and the cover flow come from.

Build your own

It is a widget. Take it.

The terminal ships in the Starling SDK, so your app can have one too — shell, escape sequences, fonts, scrollback and selection included. A whole terminal app, in full:

main.swift
import ExampleHost
import Flutter

let session = TerminalSession()
session.startShell()

runExampleApp(title: "Terminal", width: 940, height: 620) {
    TerminalView(session: session)
}

The workspace in the films above is that widget with geometry around it — splits, frames and a cover flow, and no terminal code of its own.
